# tether/broker

Import: github.com/xraph/tether/broker

The multi-tenant MQTT broker: one mochi-mqtt v2.7.9 server, one Tether hook. Every network client is resolved to a tenant at CONNECT, and its client ID and every topic it sends are prefixed with the tenant ID (a `ttnt_...` TypeID) server side. The prefix comes off again on every PUBLISH the client receives.

## API

- `(*Broker).MaxPacketSize() uint32`: the Maximum Packet Size the broker accepts: `Config.MaxPacketSize`, or in cluster mode less when the cell's NATS server cannot carry it (`fitPacketSize`: (max_payload - 16 KiB) x 3/4, so any packet fits as a log entry with Tether's headers and as a retained value, base64 in JSON; logged at Warn). Mochi v2.7.9 never puts it on a CONNACK, so in cluster mode OnPacketEncode sets it on every 5.0 success CONNACK (R53, so a client knows before it sends a packet over it); without a cluster the CONNACK carries none, as before. The extension bounds the HTTP publish with it.
- `Config{TCPAddress string; TLS *TLSConfig; WebSocketAddress string; DataDir string; MaxSessionExpiry time.Duration; MaxPacketSize uint32; MaxTopicLength int; MaxInflight uint16}`, yaml/json snake_case. `TLSConfig{Address, CertFile, KeyFile string}`.
- `DefaultConfig()`: TCP `:1883`, session expiry cap 7 days, packet 1 MiB, topic 1024 bytes, 1024 in-flight messages per client (`DefaultMaxInflight`, mochi's `Capabilities.MaximumInflight`; mochi's own default is 8192), no TLS, no WebSocket, no persistence. `New` fills zero limits with these defaults. At least one listener is required.
- `PermLoader`: `Load(ctx, *auth.Identity) (acl.Rules, roleIDs []string, error)`. Called once per CONNECT (twice when a change was announced meanwhile, see Admin reactions) and again on every reload. roleIDs must list every role the rules came from, inherited ones included: `ReloadRole` finds connections by them. At CONNECT any error refuses with 0x88. On a reload an error wrapping `auth.ErrBadCredentials`, `auth.ErrNotAuthorized`, `tether.ErrNotFound` or `tether.ErrInvalidInput` disconnects with 0x87; any other error keeps the previous grants for now and starts a retry (see Admin reactions).
- `Deps{Auth auth.Authenticator; Perms PermLoader; Limits *limits.Limiter; Logger *slog.Logger; Metrics Metrics; Cluster *Cluster}`. Auth and Perms are required; nil Limits gets `limits.New()`, nil Logger discards, nil Metrics reports nothing. mochi logs through the same logger (`component=mochi`). Nil Cluster runs the broker alone, exactly as before clustering existed; see Cluster mode below.
- `Metrics` (metrics.go): node-wide counters, no tenant. `ConnectionOpened()` when a connection takes a fresh tenant slot (`acquireSlot`), `ConnectionClosed()` when it releases it (`clientState.releaseSlot`, once); a takeover that inherits a slot reports neither, so opened minus closed is the live connection count. `MessageIn()` next to the tenant's in counter (OnPublish), `MessageOut()` next to its out counter (OnPacketEncode). `AuthFailure(reason)` on every refused CONNECT (`hook.refuse`), reason from the CONNACK code: `AuthReasonBadCredentials` "bad_credentials", `AuthReasonNotAuthorized`, `AuthReasonUnavailable`, `AuthReasonRateLimited`, `AuthReasonConnectionLimit` (0x97), `AuthReasonInvalidWill` (0x90), `AuthReasonOther`. `ACLDenied(op)` on every false OnACLCheck for a network client: `ACLOpPublish` "publish" for writes, `ACLOpSubscribe` "subscribe" for reads (SUBSCRIBE and deliveries). Called on mochi's goroutines: implementations must be concurrent-safe and quick. The extension maps them to forge metrics.
- `ClusterMetrics` (metrics.go), optional: a `Deps.Metrics` that also implements it gets a cell node's counters (found by type assertion in `New`, cluster mode only; otherwise `noClusterMetrics`). `ClusterFenced(bool)` from `onFence` (after the fenced flag flips on) and `onUnfence`; `LogAppended(time.Duration)` registered on the node's Log with `cluster.Log.OnAppend` (every committed append, send to commit); `CASLost()` registered on its Sessions with `cluster.Sessions.OnLostCAS` (every losing session write, an Acquire's internal retry included); `ReplayMessage()` next to the `replayed` counter (cursor.go). The registration replaces any observer already on a Log or Sessions the caller passed in. No tenant on any of them.
- `New(cfg, deps) (*Broker, error)`: validates, opens nothing. Errors wrap `tether.ErrInvalidInput`.
- `(*Broker).Start(ctx)`: opens its own listeners (so `Addr` is real), adds the hook, then mochi's badger storage hook when `DataDir` is set and there is no cluster (with a cluster it logs one Info line and ignores `DataDir`), then `lastHook`, then (cluster mode) creates the injector and starts the retained writers, then serves, then (cluster mode) starts the idle sweep of log readers and retained caches. Start once; a second call wraps `tether.ErrConflict`.
- `(*Broker).Stop(ctx)`: stops the $SYS publisher and the reload retries, stops injecting (cluster mode) and stops every log reader and retained cache, stops accepting, disconnects clients (their pending QoS 1/2 acks are abandoned), waits for them, closes mochi and storage, then (cluster mode) stops the delayed wills and reclaims (`stopLive`), drains the queued retained writes (each bounded by `retainedDrain`, 2 s from then), stops the session watch and flusher, and then closes a Router the broker made. Returns ctx's error if ctx ends first. No-op when not started or already stopped.
- `(*Broker).Running() bool`: true from a successful Start until Stop. The admin operations below answer `tether.ErrNotFound` or `tether.ErrConflict` when it is false, so a caller that must tell "stopped" from "no such thing" (the REST layer answers 503) checks it first.
- `(*Broker).Addr() net.Addr`: the TCP listener's address, nil if none.
- `(*Broker).ClusterHealth(ctx) error`: nil alone or when the node can act for its cell; wraps `cluster.ErrFenced` or `cluster.ErrUnavailable` otherwise (see Liveness).
- `(*Broker).Stats(tenantID string) Stats`: `Stats{Connected, Sessions, Subscriptions, Retained int; MessagesIn, MessagesOut, BytesIn, BytesOut uint64}` for one tenant on this node. Connected, Sessions (open plus kept offline sessions) and Subscriptions come from mochi's clients, Retained from mochi's retained messages in the tenant's namespace; each call walks both once. MessagesIn counts the tenant's PUBLISH packets that passed the ACL and the rate limit; MessagesOut counts PUBLISH packets written to the tenant's network clients ($SYS stats included). BytesIn and BytesOut are the payload bytes of those same packets. Counters start at zero with the process. Before Start and after Stop only the counters are filled.
- `(*Broker).Usage() []TenantUsage` and `(*Broker).StartedAt() time.Time` (`usage.go`): metering. `TenantUsage{Tenant string; Connections int; MessagesIn, MessagesOut, BytesIn, BytesOut uint64; ConnectionTime time.Duration}`. `Connections` is the tenant's live network connections on this node; every other field is cumulative since Start (`StartedAt`, the zero time before it). `Usage` lists every tenant seen since Start (one that connected or had traffic counted; `countersFor` makes the entry), sorted by tenant ID, with `ConnectionTime` integrated up to the call. It copies the counter pointers under `countersMu`, then reads atomics and each tenant's `connClock` mutex: no mochi or NATS call, no lock the PUBLISH path takes. Counting rules: bytes are PUBLISH payload bytes only (topic and properties excluded), added next to the message counter they belong to (`OnPublish` accepted, `OnPacketEncode` delivered, `DevicePublish`); a plain `Publish` is not a message in (as in `MessagesIn`), so it adds no bytes in either; `$SYS` publishes count as out like `MessagesOut`. Connection time is per tenant: `connClock` holds the live count and the time of its last change, and each change adds count x elapsed. The count follows the connection slot: `hook.acquire` (a fresh slot) opens, `clientState.releaseSlot` (held to released) closes. A takeover that inherits the old connection's slot (`transferSlot`, only at the tenant's limit) changes nothing, and a `returnSlot` that hands the slot back changes nothing. Without a limit a takeover takes a second slot for the moment before the old connection's OnDisconnect gives its own back, so `Connections` reads 2 for that moment. A connection refused after it took a slot is counted for the time it held it.

Listeners: TCP and TLS use `net.ListenConfig` (TLS through `tls.NewListener`, TLS 1.2 minimum) wrapped in `listeners.NewNet`. WebSocket uses mochi's `listeners.NewWebsocket`, which binds `WebSocketAddress` itself and answers with subprotocol `mqtt` on any path; its real port is not exposed, so give it a fixed one.

Mochi options: `InlineClient: true`; capabilities `TopicAliasMaximum: 0`, `MaximumSessionExpiryInterval` from config (seconds), `MaximumPacketSize` and `MaximumInflight` from config.

## Hook (hook.go)

Provides exactly OnConnectAuthenticate, OnACLCheck, OnSessionEstablish, OnPacketRead, OnPacketEncode, OnPublish, OnWill, and in cluster mode also OnSubscribe, OnSubscribed, OnUnsubscribed, OnClientExpired, OnSessionEstablished, OnQosPublish, OnQosDropped, OnPublishDropped and OnSelectSubscribers (`clusterProvided`; `Provides` answers false for them without a cluster). It must stay the only provider of OnConnectAuthenticate and OnACLCheck (mochi ORs them). A second hook, `lastHook` (ID `tether-last`), provides only OnDisconnect and is added after storage; see OnDisconnect below. What each hook adds in cluster mode for QoS 1 and 2 is under "QoS 1 and 2 through the log" below.

- OnConnectAuthenticate: `Auth.Authenticate` (Credentials.ClientID is the raw or mochi-assigned ID), refuse a nil or disabled tenant, refuse credentials whose `Identity.ExpiresAt` has passed (0x86), `Perms.Load`, `acl.Compile` with `Vars{ClientID: raw ID, Username}` (dropped grants logged once), refuse a will whose topic fails `topic.Valid` or the publish check (0x90 and 0x87; in cluster mode also a will topic over the cell's 1024 byte cap, `subject.CheckTopic`, ruling R13: 0x90), then check the tenant's session cap (`sessionRoom`: with `Limits.MaxSessions` set, a client ID with no session in mochi's `Clients` is refused with 0x97 when the tenant already holds that many sessions, open plus kept offline; it walks mochi's clients, so it costs O(clients) per CONNECT for those tenants, and two CONNECTs racing for the last session can both pass), then take a tenant connection slot and register the state, unless DeleteSession is deleting the session of that namespaced client ID (the registry's `deleting` tombstone, checked and registered in one step by `addUnlessDeleting`): then 0x88. State is stored per `*mqtt.Client` (`clientState`: identity, tenant snapshot and grants are atomic pointers to immutable values, so the hot path takes no lock; `connectedAt`, `expiryCap` (the lower of the broker's cap and the tenant's `MaxSessionExpiry`, whole seconds), `sessionExpiry` (the CONNECT's session expiry held to `expiryCap`; 3.1.1 clean = 0 and persistent = `expiryCap`) and `expiryShortened` are set before the state is registered and never change). If `Broker.changes` moved while this ran, the whole authorization runs again under the state's `reloadMu`, now that the state is visible to every later reaction; a refusal then removes the state and releases the slot. Finally, when `Identity.ExpiresAt` is set, a timer disconnects the client at that time with 0xA0 (`packets.ErrMaxConnectTime`, maximum connect time); it is stopped when the state is removed (OnDisconnect, sweep, stale bind) and when another connection takes the session over (`registry.bind`).
- Cluster CONNECT whose session record write is too large for the cell (`cluster.ErrTooLarge` from `acquireSession`, say a record with many subscriptions plus a will) is refused 0x95; any other failure to take the session is 0x88.
- CONNACK codes. Mochi always answers a false OnConnectAuthenticate with 0x86, so the hook records the code it wants per client and OnPacketEncode rewrites that CONNACK's reason code (and reason string) on its way out. 5.0: 0x86 bad credentials, 0x87 not authorized (auth error, disabled tenant, will outside the grants), 0x88 unavailable (auth outage, permission load failure, no tenant, session being deleted), 0x9F auth rate limited, 0x97 tenant connection or session limit, 0x90 invalid will topic. 3.1.1: 0x04 for bad credentials, 0x03 for 0x88/0x97/0x9F, 0x05 for the rest.
- Slot takeover: at the tenant's limit, after sweeping closed connections, a client reconnecting with a client ID a live connection owns inherits that connection's slot (mochi is about to take the old one over), so a device can always replace its own connection. A takeover refused after that (a delete of the session in progress, or authorizing again after a change fails) gives the slot back to the old connection, which is still open (`clientState.returnSlot`; the slot state is an atomic held, transferred or released), and releases it only when the old connection has gone meanwhile.
- OnSessionEstablish: `cl.ID = <tenant>/<raw ID>` (before mochi's session lookup, so takeover, storage and `Clients` use it; nobody can collide with another tenant or with mochi's `inline` client); namespaces the will topic; sets `Props.TopicAliasMaximum = 0`; `capSessionExpiry`: a 5.0 `Props.SessionExpiryInterval` above `expiryCap` is lowered to it (mochi then builds its CONNACK from that, and OnPacketEncode adds the Session Expiry Interval property to the success CONNACK when `expiryShortened`), and a 3.1.1 persistent session gets `Props.SessionExpiryInterval = expiryCap` with the flag set (badger stores it). A client mochi assigned an ID keeps the un-prefixed one in its CONNACK. `registry.bind` returns the previous owner when it is still open (mochi is about to take it over), and the hook gives that connection's writes a deadline of `takeoverWriteWait` (`disconnectWait`, 1 s; `clientState.boundWrites`): mochi writes its 0x8E DISCONNECT under the old client's write lock before the new CONNACK, and a peer that stopped reading leaves a write (the replay's, a shared delivery's, mochi's own) blocked under that lock, which held the takeover until the old connection's keepalive ran out, or for good with keepalive 0. mochi resets that deadline before each packet it reads, so the connection is also closed after `takeoverWriteWait` unless mochi has stopped it by then (a peer that stopped reading but still sends QoS 0 or PUBACKs).
- OnPacketRead (network clients): in cluster mode a PUBREL frees its QoS 2 receive slot and clears the session's pending entry before mochi answers it (clusterlog.go); and the topic of a PUBLISH and every SUBSCRIBE and UNSUBSCRIBE filter must also pass `subject.CheckTopic` (1024 bytes before namespacing, the cell's limit whatever `MaxTopicLength` says), refused the same way as an invalid one below (ruling R13). A 5.0 DISCONNECT that raises the session expiry above `expiryCap` is held to it. A client with no state has its DISCONNECT passed through unchanged (refusing it would end the read with an error and mochi would publish the will) and every other packet refused with `packets.ErrRejectPacket`. PUBLISH with an empty topic (alias only), or one failing `topic.Valid(name, false, MaxTopicLength)`, is rejected with `packets.ErrRejectPacket`, after a DISCONNECT for 5.0 clients (0x94 alias, 0x82 no topic, 0x90 invalid or too long). No ACL check ever sees it. Otherwise the topic is namespaced. SUBSCRIBE and UNSUBSCRIBE keep their filter count: valid filters are namespaced, an invalid or over-long one becomes "", which mochi refuses with 0x8F before the ACL check.
- OnACLCheck: inline client allowed. Otherwise strip the client's tenant (`topic.Strip`; outside the namespace is denied, which also hides mochi's global `$SYS/broker/...` and every other tenant's `$SYS/<tenant>/...`), strip `$share/<group>/` for reads, run `topic.Valid`, then `CanPublish` (also refusing anything starting with `$SYS`, as mochi does) or, for a read, allow the tenant's own `$SYS` (the relative name is `$SYS` or starts with `$SYS/`, exact case; no grant needed) and otherwise `CanSubscribe`. A client with no state that is closed (a kept session, live-disconnected or restored from storage) gets read access to names in the tenant of its namespaced ID only, so deliveries queue for offline sessions; the grants were checked when the subscription was made.
- OnPacketEncode: PUBLISH to a network client gets `topic.Strip`ped with its tenant and is counted as a message out for that tenant. Cluster mode: a PUBLISH tagged as retained (`retainedTag`) gets its retain flag set for a 5.0 client holding a matching subscription with Retain As Published (`retainAsPublished`, any of overlapping ones; [MQTT-3.3.1-12/13]). A name that does not strip (should not happen: delivery passed the ACL) fails closed (`withhold`): the client is stopped with 0x83 implementation specific error, which closes its connection before mochi writes, and the packet becomes `$tether/withheld` with no payload and no properties, so neither the other tenant's topic nor its data leaves. Not counted. A PUBLISH that is delivered also has `Mods.DisallowProblemInfo` cleared: mochi v2.7.9 sets it for a client that connected with Request Problem Information 0 (paho.golang's default) and then drops the publisher's user properties from every packet, PUBLISH included, though [MQTT-3.1.2-29] only restricts the other packet types. A 5.0 subscriber gets the user properties whatever it asked for. Cluster mode: a PUBLISH over the client's Maximum Packet Size (`tooLarge`, measured as WritePacket will encode it, stripped topic and problem information included) is discarded as if delivered [MQTT-3.1.2-25] (`discardOversized`, counted in `clusterNode.oversized`, logged at Info): out of the inflight map with the send quota restored, complete for the session (`onAck`, so the cursor passes it) or, untagged, for its shared group (`shareDropped`); the hook returns the measured packet, so mochi's own size check fails the write and nothing goes out. The replay's writer takes `ErrPacketTooLarge` as sent, not as a dead connection, and `shareWriteFailed` leaves a QoS 1 or 2 one to the hook. Without a cluster mochi's behaviour stays (the entry stays in flight).
- OnPublish: guard that the namespaced topic is still the client's after alias handling. Then one token from the tenant's budget (`limits.AllowMessage(tenant, tenant.Limits)`, per tenant per node, shared by its connections). Over the budget: a 5.0 QoS 1 publish returns the bare `packets.ErrQuotaExceeded` (PUBACK 0x97; mochi type-asserts the code, so never wrap it); everything else returns `packets.ErrRejectPacket` (dropped, no ack), because mochi publishes a 3.1.1 or QoS 0 message anyway on any other error and would answer QoS 2 with a PUBACK. Accepted publishes count as messages in. The inline client is never limited or counted. Cluster mode: an accepted QoS 0 publish of a network client also goes to `Router.Publish` (tenant, tenant-relative topic, `clusterProps`) before mochi delivers it locally; a QoS 0 publish of mochi's inline client (the host's Publish, DevicePublish, DeleteRetained) is routed the same way unless the injector made it (recognised by pointer) or its name is the tenant's `$SYS` (per-node stats stay on the node) or no tenant's. QoS 1 and 2 go through the log instead (see "QoS 1 and 2 through the log"). A retained publish never reaches mochi's store in cluster mode: a network client's QoS 0 one is applied to this node's cache and queued for the cell's retained store (`retainPublish`), the inline client's was written by the admin call itself, and both go on to mochi with the retain flag clear and tagged (`tagRetained`); see "Retained messages".
- OnWill: mochi calls it as it is about to publish a will, which skips the publish ACL check. The will's topic is checked against the client's current grants; one no longer granted (or a client with no state) is replaced by a will on `$tether/withheld` with no payload, QoS 0, not retained, which no tenant filter matches and no ACL check passes (mochi ignores errors from this hook, so it cannot be told to drop the will). In cluster mode a granted will of a network client goes to the cell instead (`clusterWill`, see Liveness), and mochi always gets the withheld will: a QoS 0 will is delivered on this node by the injector, a QoS 1 or 2 one by this node's log reader.
- On the success CONNACK of a connection with `SessionPresent` (OnPacketEncode, the only point between mochi's session takeover and its resend of inflight messages): `pruneSession` removes the inherited subscriptions and queued PUBLISH inflights the connection's grants no longer allow (an offline session receives anything in its tenant, so a grant revoked while the device was away is enforced here).
- OnDisconnect (`lastHook`): releases the slot, drops the state and closes `clientState.ended`. Cluster mode: dropping the state closes the connection's `pubPipe` (`registry.remove` calls `closePipe`; pending QoS 1/2 publishes abandoned, no ack), and, when mochi says the session ends with the connection (`expire`) and no other client holds the ID, drops the session's pending QoS 2 entries. Mochi runs a hook event on hooks in the order they were added, so this runs after badger's OnDisconnect has written the session's final record; DeleteSession waits on `ended` before it deletes the record. Only this (and a refusal at CONNECT, via `registry.remove`) closes `ended`: `sweepClosed` and a stale `bind` move the state to the registry's `closing` map, where OnDisconnect still finds it; entries older than `closingTTL` (1 min) are forgotten, since mochi skipped OnDisconnect for them. Mochi also calls it for sessions it restores from storage; those have no state. Cluster mode: then `endSession` (see Sessions).

## Cluster mode (cluster.go)

`Cluster{Conn *cluster.Conn; Config cluster.Config; Sessions *cluster.Sessions; Log *cluster.Log; Members *cluster.Members; Retained *cluster.Retained; Shared *cluster.Shared; Control *cluster.Control}` as `Deps.Cluster`. Conn is required and Config must be enabled and pass `Validate` (else `New` wraps `tether.ErrInvalidInput`). The broker closes none of them except its Router and a Shared it made. Log nil: `New` makes one on Conn (`cluster.NewLog`); Sessions and Retained nil likewise (`cluster.NewSessions`, `cluster.NewRetained`). Members, when set, gets the broker's OnFence, OnUnfence and OnPeerDead callbacks registered in `New` (see Liveness); the caller starts it after the broker's Start and stops it after the broker's Stop. Nil Members: the node never fences itself and never takes over for a dead node. The Router is always the broker's own (unexported `clusterNode.router`; the caller-supplied Router field and the exported `DeliverRouted` are gone, since nothing outside supplied one): `New` makes it on Conn with `Config.NodeID` and `(*Broker).deliverRouted` as its deliver, and Stop closes it after mochi is down (so the last clean sessions still release their routes). Shared nil: `New` makes one on Conn over Log (`cluster.NewShared`) and Stop closes it after mochi is down; one you set yourself you close, after the broker's Stop. Control, when set, gets the broker's tenant.updated, session.kick and session.delete handlers subscribed in `New`; the caller starts it after New and after every other handler is on it (the events reactor, the tenant cache eviction), before the broker's Start, and stops it after the broker's Stop. Nil Control: tenant changes stay on this node, and Kick and DeleteSession of a session another node serves behave as before (see Control bus).

- Injector: `srv.NewClient(nil, mqtt.LocalListener, "tether-cluster", true)` with ProtocolVersion 5 (so mochi keeps the properties), created in Start just before mochi serves (so a log reader started for the first client has somewhere to deliver), never in mochi's clients map, stored in an atomic pointer; the hook recognises it by pointer (`clusterNode.isInjector`), since mochi's own inline client is inline too. `(*Broker).inject(tenantID, name, payload, qos, props, origin, seq, retain)` builds a PUBLISH on `topic.Namespace(tenantID, name)` (the `$` rule included) with `packetProps(props)` and calls `srv.InjectPacket`, so local delivery, OnACLCheck on every delivery and the outbound stripping run as for any message; inline means no rate limit, nothing counted in, never routed or appended again. QoS 1 and 2: mochi's processPublish takes an inline publish of any QoS as already received (the inline branch fans out and returns before the receive quota, the inflight map and any ack), delivers at min(qos, subscription) and keeps no state for the injector; `PacketID` 1 only passes mochi's validation (`TestInjectQoS12KeepsNoState`). `retain` never sets the packet's retain flag (mochi would store it): it tags the packet (`tagRetained`, `pk.Connect.WillRetain`, copied into every subscriber's packet and never encoded) for OnPacketEncode's Retain As Published. `origin` (a namespaced client ID, or "") rides in `pk.Connect.ClientIdentifier`, which a PUBLISH never uses, and OnPublish moves it into `pk.Origin` (`injectedOrigin`), because mochi overwrites the origin with the injector's ID first: that keeps No Local working for messages from the log. A read-write gate (`clusterNode.gate`) holds the server: Stop clears it before mochi shuts down, so nothing is injected into a closing server; before Start and after that inject returns `errNotInjecting`.
- `(*Broker).deliverRouted(tenantID, name string, payload []byte, props cluster.Props, retain bool)` (unexported): a routed QoS 0 message in, with its retain flag (the Router's `Tether-Retain` header, ruling R33b), which only tags the injection for Retain As Published. It comes off NATS, so it is checked: a tenant ID that is not canonical, a name failing `topic.Valid(name, false, 1024)` (wildcards, `$share`) and a name under `$SYS` in any casing are dropped and logged at Warn. Then `inject` at QoS 0. It runs on the Router's dispatch goroutines and does not block: mochi queues each delivery on the subscriber's outbound channel (dropping when full, as for any QoS 0).
- Routed QoS 0 order: the Router delivers each topic's messages in publish order even through overlapping filters (cluster ruling R19), and `inject` hands each to mochi synchronously, so per-topic order holds into mochi's outbound queues.
- Routes (refcounted Router interest). OnSubscribed (network clients only: not mochi's inline client, not the injector) takes one reference per filter mochi accepted (code below 0x80), as (client's tenant, tenant-relative filter); a shared filter joins its group instead (see "Shared subscriptions"). The references live in `clusterNode.routes`, keyed by namespaced client ID (the session, so a persistent takeover keeps them) then filter, at most one per session and filter, so a repeated SUBSCRIBE holds no second one. Mochi writes the SUBACK from the same `reasonCodes` slice right after OnSubscribed, so a filter whose `Router.Subscribe` fails is refused in place: code 0x80 (also the 3.1.1 failure code), mochi's subscription removed (`Topics.Unsubscribe`, `Info.Subscriptions`, `State.Subscriptions.Delete`), no retained messages (mochi skips codes from 0x80), Warn log with tenant and filter, `routeErrors` counted.
- Releases, all through `clusterNode.release(nsID, tenant, filters)` (`releaseAll` lists the session's filters and calls it): the entry is removed under `routesMu`, so each reference is given back exactly once and a repeated release does nothing. OnUnsubscribed releases the filters the session no longer holds (mochi also calls it for a refused UNSUBSCRIBE and for filters never held): an UNSUBSCRIBE, a clean session that ended (mochi's UnsubscribeClient on disconnect, Kick included), a clean takeover. OnClientExpired (mochi's 5.0 expiry deletes the session without unsubscribing it) releases all, unless another client holds the ID. `Broker.unsubscribe` (pruning after a reload or a reconnect, DeleteSession and the 3.1.1 expiry sweep through `purgeSession`) releases what it removed (`releaseRoutes`). A persistent session that goes offline is evicted from mochi, and its end releases all its references (`finish`, see Sessions); so does the end of a session that still held subscriptions out of the index for a replay.
- A reference is pending while `Router.Subscribe` runs; a release that finds it pending skips the Router and the subscriber gives it back when its call returns, so no Router call ever runs under `routesMu` or the registry lock. Router calls from a reload's pruning run under the connection's `reloadMu` (per connection). The CONNACK-time prune runs in OnPacketEncode, which mochi calls before it takes the client's write lock (`cl.Lock()` comes after encoding in `WritePacket`), so those Router calls hold no mochi lock.
- Prune racing a SUBSCRIBE: mochi stores a subscription before OnSubscribed runs, and a reload's prune (host goroutine, `reloadMu`, which the client's read loop does not take) can remove it in that window and find no reference to release. After a successful subscribe, OnSubscribed checks `cl.State.Subscriptions` again and releases the reference when the filter is gone; a prune after that finds the reference itself. release being idempotent, both may run.
- Props (ruling R3): `clusterProps(packets.Properties) cluster.Props` and `packetProps(cluster.Props) packets.Properties` map user properties (order and duplicate keys kept), content type, response topic, correlation data, message expiry and payload format (the flag becomes a non-nil pointer and back).
- Counters for tests: `clusterNode.published` (successful Router.Publish calls), `routeErrors` (failed Router calls of any kind, each also logged at Warn). `clusterNode.routed(nsID)` lists a session's routed filters.
- The retain flag of a routed QoS 0 message travels (`publish` passes `Retain` or the hook's tag to `Router.Publish`, R33b), so a Retain As Published subscriber on another node gets it set. The retained message itself reaches every node through the cell's retained store (see "Retained messages"); the routed copy never touches a cache. Log messages carry the flag too.

## Sessions, cursors and takeover (clustersession.go, cursor.go)

Cluster mode only. Spec "Persistent sessions and cursors" and "Ownership, takeover and liveness", spike 1 answers 1 and 2.

- Ownership: every CONNECT takes its key in the session bucket (`cluster.Sessions.AcquireWith`) as the last step of OnConnectAuthenticate, after `ensureReader` (`acquireKey`, ruling R27): a lost CAS is read again; if the record still has the epoch the attempt read, the owner's own write moved the revision, so it retries with backoff (5 ms doubling to 100 ms) for up to 2 s; if the epoch moved, another CONNECT took the key: the first time (a simultaneous connect) this later one takes it over, a second time it is refused. Failure refuses 0x88 (state removed, slot returned). A resume that fails after the acquire (`loadSession`, e.g. reading the log) gives the key back (`giveBack`, ruling R28): the record as it was, owner "", no will, the previous expiry as TTL. Before that, a raw client ID failing `subject.CheckClientID` is refused 0x85 (3.1.1: 0x02) with no KV call (R13). The record written carries owner, epoch, clean flag, protocol version, username, device ID, expiry, the CONNECT's will (tenant-relative topic, for Task 10), and either the previous record's session state (resumed) or a fresh one (also when the previous record's session expired, which a key holding a delayed will can outlive: see `willKeyTTL` under Liveness) with `Cursor` = the tenant's live position. One `session` per namespaced ID the node owns (`clusterNode.sess`, under `sessMu`); `sessionLocks` serialises the work on one ID (CONNECT from the acquire to the end of OnSessionEstablish via `clientState.sessUnlock`, a session's end, a takeover check, a delete). It is held across NATS calls, never with the registry lock.
- Tracked sessions (`session.tracked`, an `atomic.Bool`: set at CONNECT, and by a handover that makes a clean session persistent): persistent (`sessionExpiry` > 0) or resumed from a persistent record. They have a cursor, replay, and persist; clean ones only own their key and delete it when they end (in the background, CAS on the last revision).
- Resume (`establish`, `loadSession`): no local copy and a previous record with expiry > 0 and clean start false: the subscriptions the grants still allow go to `session.loaded` (held out of mochi's index) and take their QoS 0 routes; outbound QoS 2 still in flight (`QoS2Out`) becomes the inflight of an offline mochi client built the way loadClients does (`materialize`: `NewClient(nil, listener, id, false)`, expiry, `Stop`, `Clients.Add`), PUBREL for state 1, the PUBLISH read back from the log for state 0 (one ranged replay, `fetchLogs`, own 10 s bound), each tagged with its sequence; `QoS2Done` and those sequences go to `session.skip`; the replay also passes over everything up to the record's `DoneThrough` (`skipThrough`) except its `Pending` (`redo`, minus what was restored or completed); `QoS2In` seeds `qos2In`. mochi's inheritClientSession takes the offline client (session present). A live local session of the node is handed over instead (`handOver`: the session object moves to the new connection, mochi moves subscriptions and inflight). mochi clones the old connection's inflight map but goes on delivering to the old connection until `Clients.Add`, so a live log delivery injected in between reaches the old connection only; at the CONNACK (`established`, `recoverHandover`) every entry of the session's deliveries that the new connection's inflight map does not hold under the same packet ID and sequence is dropped from the books and the session pinned below it, so a repin replays it (counted in `handoverLost`; a QoS 2 flow at PUBREL is held when the map has a PUBREL under the ID and `QoS2Out[id]` is at PUBREL for that sequence, since mochi's PUBREL carries no tag and a replay would send the message again as a new PUBLISH; `followShare` does the same for shared deliveries). A closed leftover in mochi, or the connection of a session lost to another node, is evicted first. A clean start replaces the old session (replay stopped, routes released).
- Cursor: highest log sequence such that every earlier message of the tenant was acked (if it matched) or did not match; QoS 0 plays no part. `deliverLog` holds `tenantTrack.mu` around each injection and then moves `livePos`. Injected packets carry the sequence in `pk.Connect.WillTopic` (`tagSeq`/`seqOf`; mochi copies it into each subscriber's packet and never encodes it), so OnQosPublish records `session.out[packetID] = seq`; PUBACK and PUBCOMP read in OnPacketRead complete it (independent of mochi's inflight bookkeeping). A live session's cursor is `max(livePos, liveFloor)` held below every delivery in `out` and below `pin`. Pins: a delivery mochi could not queue (OnPublishDropped), an inflight map full before a message (`tenantTrack.full`, `pinFull`: mochi drops silently; `noteFull` marks a full map from every path that fills it: mochi's deliveries and the replay writer; the paths outside the tenant lock, an inbound QoS 2 reservation (`commitPublish`) and a takeover's clone (`established`, with the live position `handOver` read before the clone), use `pinIfFull`, which pins a full live session at the live position read before the map grew, since the next message may already have been dropped), a packet ID mochi reused, an injection that failed (`pinAll`). So the cursor never passes an unacknowledged or dropped message. A pin does not last: `repin` takes the live session out of the index under the tenant lock and replays it from the pin (deliveries in flight, those completed after the pin and `qos2Done` marked not to send again), waiting for the window like any replay, and the session goes live again with the pin cleared (at Stop it only pins). Records carry `DoneThrough` (the base) and `Pending` (deliveries in flight and queued), so `QoS2Done` holds only completions above `DoneThrough` and stays small.
- Replay (`runReplay`, after the CONNACK and mochi's inflight resend, from OnSessionEstablished): loops `Log.Replay(pos+1, max(livePos, flipFloor))`, sending matches straight to the client (`deliverDirect`, mochi's publishToClient by hand: merged matching subscriptions, No Local, read ACL, lower QoS, identifiers, message expiry from `PublishedAt`, packet ID, inflight entry), skipping `skip`. The callback only prepares and queues: each session's replay has its own writer (`replayOut`, a 64-packet buffer drained by its own goroutine) that takes the packet ID and inflight entry (mochi's `NextPacketID` needs the client lock a blocked write holds), records the delivery and writes it; until then a queued sequence holds the cursor (`session.queued`). A full buffer or window (inflight at `MaxInflight`, or the client's Receive Maximum, queued ones counted) ends that session's Replay call (`errBackpressure`), so it leaves the tenant's shared replay consumer rather than hold it, waits for room and starts its own from its position. A replay goes live only after its writer has written everything. Starting and stopping replays is serialised per session (`replayMu`); a stop abandons the writer (it registers and writes nothing more, checked under `session.mu` with each registration) and gives what it had queued back: the position goes below the first queued sequence and the deliveries in flight above it are marked not to send again. `handOver` reads the live position for `handoverPos` first (ruling R29), then switches the session's client, then stops the replay; `startReplay` does nothing at all (no stop, no `holdOut`) for a client that no longer serves the session, so a stale repin or waiting flip never stops the current connection's replay (`TestStaleStartReplayLeavesCurrentReplay`). At the CONNACK of a session taken over or restored, `orderResend` gives the tagged inflight entries `Created` values in log order, since mochi resends by whole-second `Created`. Then under `tenantTrack.mu`: `pos == livePos` flips live (subscriptions into the index, `liveFloor = pos`); `pos > livePos` (the cursor came from a node further along, or `flipFloor` from restored QoS 2) waits out of the index and `deliverLog` flips it before the first message above `pos`. Per topic: missed messages in log order, then live ones, none skipped, none sent twice. SUBSCRIBE during a replay: OnSubscribed takes the new filters out of the index again (`holdOut`, under the tenant lock); the replay matches them too (it may send a message older than the subscription). A live delivery that slipped in before `holdOut` is recorded in `skip`. Known window: between mochi's `Topics.Subscribe` and OnSubscribed a live message can overtake for that filter. A client that stops reading its socket holds only its own replay (`TestStalledReplayDoesNotHoldOthers`).
- Outbound QoS 2 exactly once across takeover: OnPacketEncode writes `QoS2Out[packetID] = {seq, 0}` to the record before a tagged QoS 2 PUBLISH to a tracked session goes out (`beforeQoS2Send`), and OnPacketRead writes state 1 before mochi answers a PUBREC with PUBREL (`onPubrec`). Each is a CAS write, so once another node has the key nothing more is sent from here: a lost write disconnects 0x8E (a failed one stops the client) and the packet is blanked. PUBCOMP moves the delivery to `QoS2Done` until the cursor passes it. A PUBREC for a QoS 2 PUBLISH the record does not track (a retained message sent at SUBSCRIBE has no log sequence; `outboundQoS2` checks the inflight map holds one under the ID) records `QoS2Out[packetID] = {Seq 0, PUBREL}` before mochi answers, so a resume anywhere sends the PUBREL (`sharedResend`) and the packet ID is never left half way. At a resume an entry at PUBREL is restored whatever the cursor (one at or below it goes in as its PUBREL only, kept out of the deliveries so the cursor does not move back). At the CONNACK of a resume with restored QoS 2, one more CAS write (`mayResend`) proves the key is still this node's before mochi resends; if not, nothing is resent. Costs: two session writes per outbound QoS 2 delivery, one per resume with QoS 2 in flight. In cluster mode mochi's write coalescing is off (`Options.ClientNetWriteBufferSize` 1, so every packet goes to the connection in its own write): with it on, a PUBLISH whose `QoS2Out` write had landed waited in the client's buffer while the next delivery's write ran, and when that write lost to a takeover the DISCONNECT 0x8E flushed it after the new owner had resent and completed it (`TestQoS2PublishNotHeldBehindNextWrite`). What remains is the gap between a write landing and the packet's own write, and a client reads its two connections in no order anyway, so a client connected twice can still see a copy on the losing connection after the flow completed on the other, under the same packet ID.
- Persistence: `runFlusher` every `flushInterval` (1 s) writes each tracked session whose record changed (`gen`) or whose cursor moved, in parallel up to `sessionWriteSlots` (64) per node; QoS 2 steps and `persistQoS2In` write at once; every write is the whole record (`snapshot`: subscriptions from the client plus `loaded`, cursor, QoS 2 maps, `qos2In`) under `session.wmu`, CAS on the last revision. A lost write reads the key from the leader first (`ownWrite`): a record still naming this node at the session's epoch means the CAS lost to this node's own earlier write, one whose wait ran out (`sessionWriteWait` 5 s is shorter than a 4 to 9 s JetStream election) and that landed later, so the node adopts that revision and writes again (up to `ownWriteRetries` 3, counted in `ownWrites`). Anything else, or a read that fails, marks the session lost (`lose`). The flusher also ends sessions whose connection mochi closed without OnDisconnect (after `closedGrace`, 2 s).
- End (`endSession` from lastHook.OnDisconnect, `finish`): only for the connection that still serves the session. Replay stopped; under the tenant lock the subscriptions are read, the session evicted from mochi (spike 1's direct `Topics.Unsubscribe`, `State.Subscriptions.Delete`, `Inflight.Delete`, `Clients.Delete`, counters adjusted, never UnsubscribeClient or ClearInflights; only when mochi still maps the ID to this client and it is not taken over) and its cursor frozen; only then is it taken out of `sess`. Routes released once, `qos2In` dropped after the last write. Then: lost or being deleted, nothing written; clean or expiry 0, the key deleted; persistent, the last record (owner "", no will, `DisconnectedAt`, expiry) with `Sessions.Expire` and the session's expiry as TTL (5 s bound, synchronous so a reconnect anywhere reads it; at Stop this needs NATS). Nothing is written after it (`session.done`).
- Takeover: `Sessions.WatchOwned` (started in Start, before serving, with a context that lives until Stop; only its first pass is bounded, by connectTimeout, and within it the bucket open and the watch's consumer create are sent again while nobody answers them) calls `onOwnedLost`, which always starts `verifyOwner` (the CONNECT that holds the key may not have registered its session yet); `verifyOwner` takes the session's lock (so an in-progress CONNECT of this node finishes first), reads the key (a failed read is retried with backoff, 100 ms doubling to 5 s, until an answer, the session's end or Stop), and unless it still names this node at the session's epoch marks it lost (`lose`): DISCONNECT 0x8E (0x98 when the key is gone), after the connection's CONNACK, bounded by `disconnect`. Its end then evicts without writing. The new owner replays from the last cursor written (QoS 1 may repeat; QoS 2 does not).
- Concurrent CONNECTs on one node (Task 8 carry): a connection that is no longer the registry owner of its ID at its CONNACK drops what mochi cloned into it (OnPacketEncode, nothing resent) and is disconnected 0x8E in OnSessionEstablished.
- Counters for tests: `evictions`, `sessionWrites`, `takeovers`, `casRetries`, `replayed`, `replaysDone`, `repins`, `ownedEvents`. Seams: `clusterNode.afterAcquire` (runs between a CONNECT's acquire and its registration), `loadHook` (fails `loadSession`) and `beforeQoS2Write` (runs in `beforeQoS2Send` right before the `QoS2Out` write).

## QoS 1 and 2 through the log (clusterlog.go)

In cluster mode every QoS 1 and 2 publish, a device's or the host's, is committed to the cell's log, and every node delivers QoS 1 and 2 to its own sessions only from the log (spike 1's async ack, rulings R21 to R24).

- Publish ACL in cluster mode: OnACLCheck answers true for every network client's write (mochi asks for write access only in processPublish, right before OnPublish), and OnPublish decides it with the same `aclCheck`, counting `ACLDenied(publish)`, so a refusal's ack waits its turn (R23; mochi would write its 0x87 at once). Refused: QoS 0 dropped; 3.1.1 QoS 1/2 disconnected (as mochi does); 5.0 QoS 1/2 get PUBACK or PUBREC 0x87 through the pipe (`ackNow`, after `admit`). Without a cluster nothing changes.
- Network client, OnPublish: guard, ACL (above), then `pubPipe.admit` (receive maximum, below), then the rate limit (a 5.0 QoS 1 or 2 over it gets PUBACK or PUBREC 0x97 through the pipe, `ackNow`, in order; 3.1.1 is dropped as before), then counted in, then `commitPublish` and `packets.ErrRejectPacket`: mochi neither acks, nor delivers, nor retains it. The `LogMessage` carries the connection's tenant (never anything the client sent), the tenant-relative topic, a copy of the payload, the QoS, the retain flag, `clusterProps`, `Origin` = node ID and `ClientID` = the raw client ID.
- `pubPipe` (one per connection, `clientState.pipe`, made in OnConnectAuthenticate): two goroutines started with the first QoS 1/2 publish. The starter takes publishes in arrival order and calls `Log.AppendAsync` (so one client's messages are committed in the order it sent them; QoS 2 first goes through the `persistQoS2` seam). The writer takes them in the same order, waits for each commit (`PendingAppend.Wait`), and writes PUBACK (QoS 1) or PUBREC (QoS 2) with `cl.WritePacket`, so acks go out in arrival order even when commits finish out of order (R23). Every send counts in `appendAttempts` (tests). Retries, after chaos finding CHAOS-1 (acks crawled at about ten a second for minutes after a leader election) and its review:
  - Late acks (`pubPipe.wait`): the writer waits for a commit for the pipe's `late` bound, `appendLate` (1 s) at first. An ack that has not come by then is taken as lost (`errAckLate`, which wraps `cluster.ErrUnavailable`: a stream leader that dies takes the acks of its in-flight appends with it) and the publish is sent again with the same message ID (JetStream stores it once). The bound is per pipe: it doubles on a late ack, up to `appendAttempt` (10 s, which also bounds the send itself and a QoS 2 session write), and halves back towards `appendLate` after a commit that came within `appendLate` (a commit that was already in when the wait began says nothing and is ignored). A log slower than 1 s therefore costs one extra send per slow spell, not one per publish.
  - Pacing (`pubPipe.pace`): the pipe's backoff, `appendRetry` 100 ms doubling to `appendRetryMax` 1 s, reset when the pipe commits. Only for an unreachable-log error (wrapping `cluster.ErrUnavailable`, late acks included): there is no wait at all when the log came back after the failed attempt went out (`logHealth.cameBackSince`), and otherwise the wait also ends as soon as the node sees the log back (`clusterNode.logDown` returns that channel). Other errors (a refused session write, an oversized message) keep the plain backoff, so they cannot spin.
  - `logHealth` (`clusterNode.logUp`, zero value ready): `down` with a `back` channel, `upAt` (when it last came back), how many pipes wait, and whether the prober runs. `up()` is called on every commit and by the prober; it closes `back` and sets `upAt`. While any pipe waits, one goroutine per node (`probeLog`) sleeps `logProbe` (200 ms) and then calls `cluster.Log.Ping` bounded by 2 x `logProbe`, until the log is up or nobody waits. Ping is STREAM.INFO, which only a stream leader answers, so the node learns the log is back without sending appends into it, and a pipe failing for a reason the probe cannot see retries at most about five times a second.
  - Queue resend (`resendQueued(headLatency)`): when a publish that had to be retried commits, in headLatency from its last send, the started publishes queued behind it go out again (in order, without waiting) when their latest attempt failed (`cluster.PendingAppend.Settled` reports an error, or the send itself failed), and, when the head committed within `appendLate` (the log answers promptly again), when they are still unanswered after more than twice that latency (at least `lostAckFloor`, 50 ms): the leader they went to died with their acks, and a client that sends nothing more would otherwise wait out a late bound for each in turn. When the head was slow the log is slow, and an unanswered publish is most likely in flight: only failures go again, so a slow log is not flooded. Nothing is read into the order answers come in: nats.go republishes by itself after a 503 and a leader answers a duplicate message ID at once.
  - A wait that began while the log was down (`logHealth.whileDown`) also ends when the node sees the log back: an attempt sent during the outage most likely went nowhere (a stream member without the leadership drops it with no answer), so it goes again at once rather than after a late bound that grew during the outage, and the bound is not doubled for it.
  - A QoS 2 publish's session write (`persistQoS2`) is not repeated once it succeeded (`pubItem.persisted`).
  - Too large (`cluster.ErrTooLarge`, which also wraps `tether.ErrInvalidInput`): a publish the log refuses as over the NATS server's max_payload is refused, not retried (`refuseTooLarge`, Warn): a 5.0 client gets its PUBACK or PUBREC with 0x83 implementation specific error (MQTT 5 has no 0x95 for those packets), a QoS 2 one's PUBREC reservation (`unreserve`) and pending entry go; a 3.1.1 client, which has no failure code to read, is stopped with 0x95. A retained publish is checked against the retained store first (`cluster.Retained.Check` in `commitPublish`, `pubItem.refused`): one the store could not hold is refused the same way before anything is appended, so a client is never told a message is retained when it is not. `fitPacketSize` makes all of this rare. Any other `tether.ErrInvalidInput` from the log is a bug: the client is stopped with 0x83.
  - When the connection ends (the registry closes the pipe, `clientState.closePipe`, before the state stops owning its namespaced ID: `bind`, `remove`, `sweepClosed`; the waits also check `cl.Closed()`), everything pending is abandoned with no ack and the client resends it on reconnect. Nothing is acked before its commit. An append refused as invalid input (cannot happen: every topic was checked) logs at Error and closes the client with 0x83.
- PUBREC reservation (`pubPipe.reserve`): a QoS 2 publish's PUBREC goes into `cl.State.Inflight` (and `Info.Inflight`) in OnPublish, as mochi's processPublish does, so mochi's `NextPacketID` never hands that packet ID to an outbound delivery while the commit runs (mochi keeps both directions in one map; `TestQoS2SelfSubscribedKeepsDeliveries`). The writer only writes it, and mochi's own PUBREL handling answers PUBCOMP (spike 1, `TestAsyncAckQoS2`). Never an ack for an uncommitted message: `pubPipe.reserved` lists the reservations whose commit was not seen, and `close` (abandoned, under `p.mu`, with `committed` deciding each item under the same lock) removes them from the inflight map. The invariant: every path that lets mochi clone a session's inflight map for a new connection has closed the old pipe first. The registry closes it (`clientState.closePipe`, under the registry lock) before a state stops owning its namespaced ID: `bind` for a takeover (in OnSessionEstablish, before mochi's `inheritClientSession`), `remove` (OnDisconnect) and `sweepClosed`. So neither the offline session nor the inheriting connection resends a PUBREC for something not in the log, also when a reconnect comes while the old connection's OnDisconnect has not finished (`TestQoS2AbandonedLeavesNoPubrec`, `TestQoS2NoPubrecInDisconnectWindow`, which holds the old connection through the unexported `Broker.disconnectHold` seam before or after its state is removed). A committed reservation stays and is resent on reconnect, rightly: a committed QoS 2 whose PUBREC was never written gets that PUBREC resent after the CONNACK, and the client's DUP of it then gets mochi's 0x91, as on standalone mochi. A same-connection DUP of a QoS 2 publish still pending gets mochi's own PUBREC 0x91 (packet identifier in use); conforming clients resend only after a reconnect.
- Receive maximum (R22): counted against the server's advertised Receive Maximum (`Capabilities.ReceiveMaximum`, mochi's default 1024; the unexported `Broker.receiveMaximum` sets it in tests). Outstanding for a 5.0 client = publishes whose ack is not written (`pending`) plus QoS 2 packet IDs whose PUBREC is written and whose PUBREL has not been read (`held`). A 3.1.1 client counts `pending` only: its PUBREL is read by the read loop that waits in admit, so counting `held` would deadlock a QoS 2 flood. A new publish at the limit: a 5.0 client gets DISCONNECT 0x93 (`disconnect`); a 3.1.1 client waits in OnPublish (its read loop, so backpressure) until a slot frees, checking every 250 ms that it is still open, and its publish is dropped if the connection ends first. Mochi's own receive quota is never spent (OnPublish rejects first), so mochi never disconnects for it.
- QoS 2 pending entries: `clusterNode.qos2In[nsID][packetID] = msgID` (`qos2MsgID`), written in OnPublish. A DUP resend reuses the entry's message ID when the entry was made for the same message, so a message committed before a drop is not stored twice (within the stream's 2 minute duplicate window); a publish without DUP, or a DUP whose topic, QoS or payload differ from the entry's, gets a fresh ID. A message ID is `rand.Text()` plus `.` and `qos2Digest` (16 hex digits of a SHA-256 over topic, QoS and payload), so the entry carries which message it was made for: a resumed record can hold an entry whose PUBREL cleared it only in memory, and a client may have reused the packet ID for a new message since, which the old ID would have JetStream discard after its PUBREC. OnPacketRead clears the entry on PUBREL (`pubrel`, which also frees the `held` slot) before mochi answers PUBCOMP. Dropped on a clean start (OnSessionEstablish), a session ending with its connection, OnClientExpired and `purgeSession`. For a tracked session (see Sessions) the starter writes the record (`persistQoS2` = `persistQoS2In`, a session write) before each QoS 2 append and again before each retry, so a DUP resend reaching any node finds the message ID; the entries are seeded from the record when a session is resumed from the cell, PUBREL marks the record changed, and they go once the session's last record is written. Other sessions keep them in memory.
- Retained: once a retained QoS 1/2 publish is committed (and, for QoS 2, its reservation kept), the writer applies it to this node's cache and writes it to the cell's retained store (`pubPipe.retain`, `storeRetained`, an empty payload deletes), waiting while the connection is open (its shard's writer retries for the 30 s window; if it gives up the write is repaired and the publish acked anyway, the message being in the log), and only then writes the PUBACK or PUBREC: an ack means "in the log and retained in the cell". When the connection ends first the write goes on in the background queue (the message is in the log; a QoS 2 client will not resend it) and no ack is written. The log carries the flag and readers deliver it live, tagged for Retain As Published.
- Host publishes (R21): `Publish` and `DevicePublish` at QoS 1 in cluster mode check `subject.CheckTopic` (as every cluster path does, R13; QoS 0 too), `Log.Append` synchronously under the caller's ctx and return its error wrapped (`cluster.ErrUnavailable` when the log cannot be reached); every node, this one included, delivers from its reader. A retained one is then written to the cell's retained store under the same ctx (`appendHost`); its error is returned too (the message is in the log by then).
- Readers (R24): one `cluster.Reader` per tenant with a connection on the node (`clusterNode.readers`, under `readersMu`, never held across a Log call). `ensureReader` runs in OnConnectAuthenticate after the authorization and before the CONNACK, starting the reader from "new" (fromSeq 0) when none runs; concurrent CONNECTs of a tenant share one start; a reader that cannot start refuses the CONNECT with 0x88. `watchReader` restarts a reader whose `Done()` closed without a Stop from `Position()+1`, logged at Warn, retrying with backoff (`appendRetry` doubling to `appendRetryMax`). A reader ends by itself when its consumer cannot be recreated or stalls (cluster/llm.txt, CHAOS-2), so a restart is how the node gets past a consumer that the meta layer left on a dead server. The sweep (`readerSweep` 10 s) stops a reader whose tenant has had no open connection (`registry.liveTenants`) for `readerIdle` (1 min); offline sessions do not hold it (Task 9 replays them from their cursor). Readers are never stopped from their own fn.
- Delivery (`logDeliver`, which calls `deliverLog` in cursor.go): the reader only reads `d.<tenant>.>`, and a message whose tenant is not the reader's, whose topic fails `topic.Valid(name, false, 1024)` or is under `$SYS` in any casing, or whose QoS is not 1 or 2, is dropped at Warn. The rest is injected at its QoS with its props, `origin` = the namespaced publisher ID and its log sequence as a tag (`tagSeq`), under the tenant's delivery lock (see Sessions). The publishing node's own subscribers get the message from its own reader, once (mochi's fan-out was rejected).
- Counters for tests: `clusterNode.appends` (commits this node saw acked, client and host), `acks` (acks written), `logDelivered` (log messages injected), `readerRestarts`. Real metrics are Task 14. `clusterNode.holdAppend` (unexported, tests) runs before each client append and can hold it, or fail it by returning an error (`appendGate` in the tests stands in for an unreachable log while the session store stays reachable; with `failing` set it refuses appends at once, as a stream without a leader does).
- Known limits: mochi writes the 0x91 for a packet ID with a PUBREC inflight directly, outside the pipe's order. Mochi's opposite collision stays, with or without a cluster: a client PUBLISH that reuses a packet ID of an outbound delivery still in flight makes processPublish delete that delivery's entry (a paho 5.0 client publishing QoS 2 to its own subscription loses about one flow in five on plain mochi). A failed append retried behind later ones of the same client can land after them. QoS 0 and QoS 1/2 of one publisher take different paths and are not ordered against each other.

## Liveness (clusterlive.go)

Cluster mode only. Spec "Ownership, takeover and liveness" and "Partitions"; rulings R18, R28, R30, R31.

- `(*Broker).ClusterHealth(ctx) error`: nil when the node can act for the cell, and always without a cluster. Wraps `cluster.ErrFenced` while fenced (the broker's flag or `Members.Fenced()`), else `Conn.Healthy`'s error, which wraps `cluster.ErrUnavailable` for a NATS connection that is down or a JetStream that has not answered for longer than Lease/2 (a meta leader election, which no node gets an answer during, does not fail it).
- OnFence (`onFence`, on the Members dispatcher, never blocking it): sets `clusterNode.fenced`, then on a liveness goroutine disconnects every network client in parallel (up to 64 at once): 5.0 DISCONNECT 0x88, 3.1.1 closed (`dropClient`). While fenced OnConnectAuthenticate refuses with 0x88 (3.1.1 0x03) before any KV call, and a CONNECT that was already on its way is dropped in OnSessionEstablished (`established`). No registry lock is held across any of it.
- Fenced writes (R31): `persist` returns `errFenced` (wraps `cluster.ErrFenced`) at once, `finish` writes nothing and `deleteKey` deletes nothing. The keys of the dropped sessions stay owned by this node with their wills and their last flushed cursor.
- OnUnfence (`onUnfence`): clears the flag and reclaims this node's own keys that no session of it serves (`reclaim(self)`), which settles the sessions dropped while fenced.
- OnPeerDead(node) (`onPeerDead`): bumps `deadGen[node]` and kicks the sweep. `sweepLoop` (started at Start when Members is set) runs `sweepDead` on every kick and once per lease: the peers `Members.Dead()` lists that this node `IsLeaderFor` and has not cleared since their last death (`cleared[node] == deadGen[node]`) are reclaimed in one `reclaimPass` (one `OwnedBy` pass for all of them); a pass with no errors marks them cleared, so steady state reads nothing. This covers a leader that dies or stops mid-reclaim and correlated deaths (n1 dies while n2, its leader in n3's view, is about to: when n2 is declared dead n3 leads for both). Start also runs `reclaim(self)` once when Members is set, for keys left by an earlier run under the same node ID (its peers saw a restart, not a death).
- `reclaimPass(nodes...)` / `reclaimKey`: `Sessions.OwnedBy(nodes...)`, then each key in parallel (16): the record's will is due `min(DelaySeconds, ExpirySeconds)` after `DisconnectedAt` (now when it was connected). Due or no will: `settle`, one CAS from the revision read: `Expire` with Owner "", no will, DisconnectedAt kept, TTL the expiry left (cursor, subscriptions and QoS 2 state kept), or `Delete` when no expiry is left (clean sessions); only a won CAS publishes the will (R18). Not due: one CAS that writes this node as the Owner and keeps the will (ruling R32), with the key TTL `willKeyTTL` (below), then `scheduleWill`. Once a CAS clearing a will is won this node holds its only copy, so the publish (`publishHeld`) runs on its own liveness goroutine, never under the session's lock or a reclaim slot (a CONNECT of that client and the sweep go on meanwhile), and retries on the broker's lifetime until it goes out or Stop. A will that can never be sent (`permanentWillErr`: `tether.ErrInvalidInput`, `nats.ErrMaxPayload`, `nats.ErrBadSubject`, JetStream 10054 message too large; a will's user properties can take it over NATS's max_payload after base64) is dropped at once and logged at Error (`errWillDropped`, counter `willsDropped`), on every path; a local will dropped that way is not owed. `reclaim(self)` (unfence, Start) retries passes with backoff (200 ms doubling to 5 s) until one succeeds or Stop and waits while fenced; for this node's own keys every key is read again under the session's lock (`n.locks`), skipped when a session of this node serves it at that epoch or a delayed will of this node waits on it (`serves`), and settled without its will when `noWill` holds its epoch.
- Invariant: a record's Owner names the node that answers for its will. Connected: the serving node. Offline with a delayed will pending: the node holding its timer. Offline otherwise: "" and no will.
- Local wills (`clusterWill`, R30): fenced: withheld, the session marked `willOwed`. Delay (5.0 only) is `min(will delay, session expiry)`, and 0 for a session being deleted or not tracked (MQTT 5: a will goes when its delay ends or its session does). Delay 0: `publishWill` under a 5 s context (QoS 0 `Router.Publish` and injected here, `local`; QoS 1/2 `Log.Append` with `Origin` node and `ClientID` the raw client ID, retried under one message ID, mochi's local publish withheld so every node, this one included, delivers it once from its reader). A failed QoS 1/2 append marks the session `willOwed` with that message ID (`willMsgID`), so the later publish of the owed will is deduplicated by the log if the append committed after all. Delay > 0: withheld; if the connection still serves its session, `session.willDelay`/`willAt` are set, the final record (`snapshot`) keeps the will with this node as Owner, written with the key TTL `willKeyTTL(expiry, due)`, and `finish` calls `scheduleWill`; if not (taken over here or elsewhere), the will is cancelled. mochi's own delayed-will path is never used (it skips every hook).
- `finish` with `willOwed` and not fenced writes nothing and runs `reclaimID` (one key, like `reclaim(self)`, after the session's lock is free). The fence is read in `finish` after the session is marked ended, under its lock, so a reclaim at the unfence either finds it ended or the unfence came first and `finish` settles it. `noWill` (nsID to epoch, memory only): `finish` marks every session end that owes no will (normal DISCONNECT, will already published or withheld, no delayed will), a deleted session's included, before its write, and the successful final write or delete clears it; a refused CONNECT whose `giveBack` write failed is marked too, and `retryGiveBack` retries that write (backoff, waits while fenced) until it goes through or loses its CAS. A new acquire of the key clears the entry. So a write that failed or was skipped while fenced never lets this node's own reclaim publish a will nobody owed. Only a real death (process gone, set lost) can still publish such a will, from a peer's reclaim.
- Key TTL of a record holding a delayed will (`willKeyTTL`): the expiry left, or the will's due time plus `willKeyGrace` (2 x (Lease + 2 s), twice the time a silent node takes to be declared dead) when that is later. A delay at or past the session expiry is cut short to it, so a TTL of just the expiry put the key's purge and the timer on the same instant: the timer then read NotFound and dropped the will as cancelled (lost every time for expiry 2 s, delay 5 s; interop `test_will_delay`). Now the key outlives the timer, and a dead holder's leader reclaim: when the will is due the settle finds no expiry left and deletes the key (or leaves it the second or so that is left, without the will), and only that won CAS publishes, so a will at the session's end goes out once, at the end. A reconnect before then still takes the key and cancels the will. The grace only shows when the holder is slow, fenced or dead: the record then outlives the session's MQTT expiry. A CONNECT in that window (any Clean Start) finds the session expired (`sessionExpired`: `DisconnectedAt` set, an expiry, and `DisconnectedAt` + `ExpirySeconds` not after now, checked on every acquire attempt) and starts fresh: session present 0, no subscriptions, cursor, pending or QoS 2 state carried, no log prefetch. Having won the key from that record it holds the only copy of the will the session's end owed, so it publishes it (`expiredWill`: not when `noWill` bars that epoch, and under the message ID of this node's old session when that one owes the will); the holder's timer then finds the new epoch and cancels. The same goes for a record without a will that a CONNECT finds in the second or so a key TTL rounds up past the expiry.
- Delayed wills (`scheduleWill`, `fireWill`, `tryFire`): one `time.AfterFunc` per namespaced client ID (`clusterNode.wills`). When due: `Get`; NotFound, another Owner, another Epoch or no will means a CONNECT took the session (anywhere) or it went: cancelled. Otherwise `settle` from that revision, and only a won CAS publishes; a lost CAS reads again, an error retries with backoff until Stop; fenced, it waits. `stopLive` (Stop, after mochi is down, before the session watch stops) stops the timers and waits for the liveness goroutines: the keys of pending wills keep this node as Owner, so the cell publishes them once this node is declared dead.
- Wills published on behalf of a record (`publishWill(local=true)`), and a client's own QoS 0 will: QoS 0 also injected here (the Router never delivers to its own node) with the client's namespaced ID as origin, tagged retained when it is. A retained will, once sent, is written to the cell's retained store and this node's cache (`storeRetained` under publishWill's ctx, handed to the background queue when that ends first), so it reaches every node. A record's will is checked like a routed message (`validWill`: canonical tenant, `topic.Valid` 1024, no `$SYS`, QoS <= 2); a bad one is dropped and logged. Test seam `willFault func() error` fails send attempts.
- Counters for tests: `willsSent`, `willsCancelled`, `reclaimed`, `fenceDrops`, `sweeps` (sweeps that read the bucket), `willsDropped`; `pendingWills()` lists the delayed wills held.
- Known gaps: after a real death of a node (its `noWill` set gone), a key whose final write it never made can still carry a will nobody owed (a normal DISCONNECT, a will already published, a refused CONNECT), and its leader publishes it. A will whose CAS was won but whose publish had not gone out when the node stopped is lost (logged at Warn by `goPublishHeld` when Stop had already begun). A held will whose publish keeps failing (retried until Stop) can still go out after its client has reconnected, since the reconnect no longer finds it in the record to cancel. The record's will is published without a fresh grant check (the CONNECT checked it).

## Control bus (clustercontrol.go)

With `Cluster.Control` (ruling R41 for tenants, R7 completed for sessions). Handlers run on the bus's one goroutine and never block it: disconnects and deletes run on goroutines (deletes through `goLive`, which Stop waits for). No lock is held across a publish or a session read.

- Tenant changes: `UpdateTenant(t)` publishes `tenant.updated` as `tenantEvent{cluster.TenantUpdated; Tenant *tenant.Tenant "tenant"}` (the snapshot travels, so a node needs no store) within `controlWait` (5 s, also bounded by the broker's lifetime) and returns; every node, the publisher included, applies it once on receipt (`onTenantUpdated` then `applyTenant(snap, async=true)`: snapshots stored at once, a disabled tenant's connections disconnected 0x98 on goroutines). An event without the snapshot (another publisher) changes nothing. A stopped broker does not publish. Publish failure: Warn, and the publisher applies it synchronously as before (`applyTenant(snap, false)`), and (ruling R51) `republishTenant` sends it again in the background with `cluster.Republish` (`republishUntil`) until the bus takes it, the broker stops (`n.ctx`), an hour has passed (counted in `republished`) or a newer `UpdateTenant` of the tenant on this node starts (`stopTenantRepublish`, one republish per tenant in `tenantRepub`, and a republish running for a snapshot with a newer `UpdatedAt` is kept when two failed changes reach `republishTenant` out of order; an attempt already under way may still land), so the other nodes get it once the bus is back and the publisher applies it a second time (idempotent). Snapshots are ordered by `UpdatedAt`, which every store moves forward with each write of the tenant (a microsecond past the stored one when the writer's clock is behind): `applyTenant` in cluster mode leaves a connection whose snapshot is newer alone (`offerTenant`, a CAS; a snapshot with a zero `UpdatedAt` always applies; without a cluster every snapshot is stored as before), so a late republish neither restores old limits nor disconnects a tenant enabled again since. Kick and DeleteSession of a session another node serves send their event through `publishSession`: a failed publish is sent again until the bus takes it or `remoteAdminWait` passes. Concurrent updates through two nodes end at the newer snapshot by store order, whatever the stream order. Key, role and subject events (the reactor's republish, package events) are order-free: a revocation is final, a grace-window expiry only ever shortens (`ExpirePrincipal`), and a reload reads the grants from the PermLoader as they are now. The service's tenant cache is evicted by `events.EvictTenantsOnUpdate`, subscribed before `New` so it runs first.
- Kick: an open local connection is kicked as before. Otherwise `kickRemote`: `subject.CheckClientID`, `Sessions.Get` (5 s); absent, offline (`Owner` ""), owned by this node with no connection, or a dead node's session a leader holds for its will (`DisconnectedAt` set, R32) is `ErrNotFound`. Owned by another node: publish `session.kick` as `sessionEvent{Tenant, ClientID, Node, Epoch}` (a superset of `cluster.SessionKick`), then `awaitRemote`.
- DeleteSession: `deleteClusterSession(srv, tenant, client, nsID, epoch, fromBus)`. Where it used to refuse a session another node owns, it now releases the session lock (the tombstone stays, so this node refuses the client ID until it returns) and calls `deleteRemote`: publish `session.delete` with the owner and the record's epoch, then `awaitRemote`. From the bus (`fromBus`) or without a Control it still refuses with `ErrConflict` naming the owner, so an event never republishes. `epoch` (non-zero from an event) must match the local session and the record, else `ErrConflict` ("the client connected again").
- Receivers (`decodeSession`): only the node the event names acts, after `sessionID` and `CheckClientID`; counters `kickEvents`, `deleteEvents`. Kick: the session in `sess` at the event's epoch has its client disconnected 0x98 on a goroutine; anything else is ignored (Debug). Delete: `deleteClusterSession(..., ev.Epoch, true)` on `goLive`, logged; this also deletes a session the node holds for a dead node's will (R32 Minor 1). Ruling R42: a delete whose record still holds a will (a delayed will waiting out its delay, the node's own or one it took over from a dead node, or one the deleted session here owes, and not barred by `noWill`) publishes it once the delete CAS has won (`publishHeld` on `goLive`, delay 0, under the owed will's `willMsgID` when the session here owes it, so the log drops a copy of an earlier attempt that committed). A connected client's will goes out when the delete disconnects it (`clusterWill`, delay forced to 0); its session's end writes nothing, so the record keeps the CONNECT's will, and `finish`'s `noWill` mark keeps the delete from publishing it a second time and stops the will's timer (`cancelWill`), since MQTT 5 sends a will at the end of its delay or of the session, whichever comes first.
- `awaitRemote(op, ...)`: reads the record every `remoteAdminPoll` (50 ms) for up to `remoteAdminWait` (5 s). Kick: the same epoch with `DisconnectedAt` set is nil (the owner keeps a session whose delayed will waits out its delay, `finish`). Still `owner` at `epoch`: keep waiting. Kick: anything else is nil (offline, ended, taken over). Delete: absent is nil; another epoch is `ErrConflict`; offline at the same epoch (the owner let it go without deleting) is deleted here at the revision read (`deleteOffline`; a lost race, such as the owner deleting the same record, reads again); held by another node at the same epoch is `ErrConflict`. Timeout: `ErrConflict` naming the node ("did not act within 5s"); the event stays in the stream and the node may still act. The caller gets "done", not "accepted".
- Test seams: `clusterNode.publishFault` (fails control publishes), counters `tenantApplied` (every `applyTenant` in cluster mode), `kickEvents`, `deleteEvents`.

## Retained messages (clusterretained.go)

Cluster mode only. Spec "Tenancy inside mochi" (retained bullet), Review Focus 5, rulings R6, R13, R24, R30.

- The cell's retained messages live in `Cluster.Retained` (one KV key per tenant and topic, `$` topics under `==<tenant>`). mochi's retained store is each node's cache of it. mochi never stores a retained publish itself in cluster mode: OnPublish takes the retain flag off every publish it lets through (network and inline) and tags the packet instead, the injector never sets it, and a client's QoS 0 will is injected rather than published by mochi; so OnRetainMessage never runs.
- Cache (`retainedCache`, one per tenant, `clusterNode.retCaches` under `retMu`): `ensureRetained` runs in OnConnectAuthenticate right after `ensureReader` and starts `loadRetained` on its own goroutine (it does not hold the CONNACK). That runs `Retained.Watch` (backoff 100 ms doubling to 5 s while it fails): the watch's first pass fills the cache before Watch returns, caught up to the store leader's mark, so every write acknowledged before the load began is in it; then the cache is ready and the watch applies every later put, delete and expiry (`applyWatched`, revision order, one goroutine). A report is checked like a routed message (`topic.Valid` 1024, no `$SYS` in any casing, QoS <= 2), dropped at Warn otherwise. Applying is `Topics.RetainMessage` of `retainedPacket` (namespaced topic, payload, QoS, props, origin = the publisher's namespaced ID for No Local, `Created` = publish time, `Expiry` = Created + the message expiry held to mochi's `MaximumMessageExpiryInterval`, the maximum when there is none, `ProtocolVersion` 5, as mochi stores a publish) or of an empty packet for a removal; never `OnRetainMessage`. `c.view` keeps what the watch last applied per namespaced topic. The cache stops with the tenant's log reader (`sweepRetained` in `sweepReaders`, no live connection for `readerIdle`) and at Stop (`closeRetainedCaches`), both through `retire`: under `retMu` (taken before a cache's `mu`, never after) each cache is marked stopped and its tenant's entries leave mochi's store before it leaves the map, so a CONNECT can only make the tenant a new cache after the clear; the watch is stopped afterwards, outside both locks.
- SUBSCRIBE (OnSubscribe, `awaitRetained`): a network client's SUBSCRIBE with a filter that can get retained messages (not shared, Retain Handling not 2) waits until its tenant's cache is ready and then caught up with the store as of the SUBSCRIBE (`syncCache` over `RetainedWatch.Sync`, R33a), both within one `retainedWait` bound (2 s, the global constraint); on the bound or a failed catch-up it goes on with the cache as it is (Info log, `retainedWaitTimeouts`). So a write any node acknowledged before the SUBSCRIBE arrived (a PUBACK, a host Publish that returned, a delete) is in the cache when mochi's own retained delivery reads it after the SUBACK (Review Focus 5, warm or cold). Catch-ups are batched per tenant: SUBSCRIBEs arriving while one runs join the next, which reads the store's mark only once they have joined (`runSyncs`, one goroutine per cache while batches remain, each Sync bounded by `retainedWait`). Cost: one or two stream-leader requests per batch. It runs on the client's read loop and holds no lock.
- Local first: a node applies its own retained publishes to its cache (`applyLocal`, when it keeps one for the tenant) before it writes them to the store, so a client that publishes a retained message and then subscribes on the same node gets it at once. This never leaves the cache stale: the write is issued after the local apply, so the watch reports it, and anything written after it, after the apply, and the last report wins (last writer by revision). Only a write that fails for good would leave the local apply behind: `repairRetained` puts back what the watch last reported for the topic (`view`), or removes it.
- Writes (`retainWrite`: tenant, `LogMessage` with Topic, Payload, QoS, Props, Origin node, ClientID, PublishedAt now). `putRetained`: `subject.CheckTopic` first (R13), then `Retained.Put` with TTL `retainedTTL` (what is left of the message expiry held to mochi's maximum, counted from PublishedAt; the cell keeps a retained message no longer than mochi would, a day by default), or `Retained.Delete` for an empty payload or an expired message. Every write of this node goes through its topic's shard (`enqueueRetained`: 16 shards by tenant and topic, each a fifo with one writer, `runRetainedWriter`), so one topic's writes reach the store in the order they were made here, whatever path they come from (a QoS 0 publish, the pipe, the host, DeleteRetained, a will). A writer stores a write with backoff (100 ms doubling to 5 s, 5 s per attempt) for `retainedRetryWindow` (30 s) from when it starts it, then logs at Warn, counts and repairs. A shard is capped at 4096; over it, or after Stop began, the write is dropped and repaired. A network QoS 0 retained publish is local apply plus enqueue (`retainPublish`, no NATS call on the read loop, nobody waits). The other writers call `storeRetained(ctx, w, handoff)`: local apply, enqueue with a `done` channel, wait under ctx. When ctx ends first, with handoff (the QoS 1/2 pipe, wills) the write goes on; without (host Publish, DeleteRetained, which return the error) a write not yet started is skipped and repaired (`cancelled`), one already started finishes regardless. Stop drains the queues after the wills, each write bounded by 2 s from then.
- Ordering: QoS 1/2 retained: commit, then (QoS 2) the reservation kept, then the store write, then the PUBACK or PUBREC. QoS 0: local apply and queue in OnPublish, live delivery by mochi and the Router at once; no ack to order against. Host: QoS 0 store first, then the live publish; QoS 1 the commit first, then the store. Wills: after the will is sent.
- Retain As Published: everything the hook or the injector took the retain flag off is tagged (`tagRetained`, `pk.Connect.WillRetain`); OnPacketEncode sets the flag for a 5.0 client with a matching Retain As Published subscription. A replayed log message (`deliverDirect`) gets it from the merged subscription (`match` ORs the option). Retained messages delivered at SUBSCRIBE come from the store with the flag set, as mochi does.
- Admin: `Retained` and `DeleteRetained` read and write the store (see Admin operations). `Stats.Retained` and the tenant's `$SYS/retained/count` count this node's cache (zero while the tenant has no cache here).
- Known gaps: a SUBSCRIBE whose catch-up runs past the 2 s bound (a store leader that does not answer, a watch restarting) goes on with the cache as it is. A QoS 0 retained publish has no ack, so nothing orders another node's SUBSCRIBE after its store write. Two nodes writing one topic at once: the store keeps the later revision and every cache converges to it, though one node's subscriber may briefly see the other value.
- Counters for tests: `retainedLoads`, `retainedApplied`, `retainedWrites`, `retainedRepairs`, `retainedDropped`, `retainedWaitTimeouts`, `retainedSyncs`; `retainedView(tenant)` lists a cache's topics. Seams: `retainedLoadHook` runs first in every load, `retainedAfterRetire` between a cache's retirement and its watch's stop, `retainedApplyDelay` slows every watch report (a lagging watch), `retainedBeforeWrite` runs as a writer takes a write (to hold a shard).

## Shared subscriptions (clustershared.go)

Cluster mode only. Spec "Shared subscriptions", rulings R5, R34, R35; cluster `Shared` (cluster/llm.txt "Shared") runs the groups.

- Bypass (R35): OnSelectSubscribers empties mochi's `Shared` and `SharedSelected` for every fan-out, so mochi's own shared selection never runs in cluster mode: neither the tenant's log reader (injector), nor a routed QoS 0 message, nor a local client's or the host's QoS 0 publish reaches a shared subscription through mochi. Shared subscriptions stay in mochi's index (mochi calls the hook only when a topic has shared subscribers) and in the session record. Ordinary subscriptions are untouched: a member that also holds an ordinary subscription matching the topic gets that copy plus, when picked, the group's (MQTT 4.8.2).
- Cursor: a shared delivery is never tagged with a log sequence, so it is never in `session.out` and a shared match counts as non-matching for the session's cursor (the group's consumer owns the delivery); the replay's `match` and `routedFilter` skip `$share` filters, so replay and repin never send for them.
- Join: OnSubscribed, for each shared filter mochi accepted (after its ACL check; No Local on a shared filter is mochi's SUBACK 0x82 [MQTT-3.8.3-4], no join), `joinShared(nsID, tenant, sub)`: the group and tenant-relative filter from the namespaced filter, `subject.CheckTopic` (R13), then `Shared.Join(tenant, group, filter, deliver)` outside every lock (a pending membership, like a pending route reference: a leave that finds it pending skips the group and the joiner leaves after Join returns). A repeated SUBSCRIBE only updates the stored subscription options. A failed join is refused in place like a failed route: SUBACK 0x80, mochi's subscription removed, Warn log, `shareErrors` counted. A filter a prune removed while the join ran is left again. Memberships live in `sharedNode.shares[nsID][namespaced filter]` (by session, so a takeover on this node keeps them).
- Leave: OnUnsubscribed and `releaseRoutes` (prunes) leave the groups of the shared filters the session no longer holds (`leaveShared`); deliveries already on their way still finish [MQTT-3.10.4-3]. `releaseAll`, the single end-of-session path (a session's end on this node: DISCONNECT, a persistent session evicted, clean start over an old session, Kick, DeleteSession, eviction, a session lost to another node, a fenced node's drop, a refused resume's `giveBack`, OnClientExpired), runs `endShared`: every membership leaves, the writer stops, and every shared QoS 1 delivery not acked goes back to its group (done with `errShareLost`, naked: another member gets it at once; MQTT allows it for QoS 1). Shared QoS 2 is the session's from the moment it is sent (see Delivery), so a session's end never gives it back. So a persistent session's membership ends with its connection; its group keeps the messages in the durable consumer, and the session resumed on any node rejoins there: `loadSession` joins the shared filters of the record (`joinLoaded`; a failure is logged and counted, the subscription stays in the record).
- Delivery (`deliverShared`, the member's `cluster.SharedDeliver`): refuses with `errShareBusy` (wraps `cluster.ErrMemberBusy`; the group tries another member, and a QoS 1/2 message nobody took comes back 250 ms later, maybe on another node) while the broker is not running, the node serves no live connection for the session, its CONNACK is not out (`session.ack`, a `connAck` per connection: replaced under `sessMu` on a takeover here, closed by `markConnacked` only for the connection that still serves the session), the membership left, the connection has no room (`outboundRoom`: the inflight map with the replay's and the writer's queued items under MaxInflight, and its outbound PUBLISH and PUBREL entries plus those queued under the client's Receive Maximum [MQTT-3.3.4-9]; it walks the inflight map) or the writer's queue (64) is full; refuses with `errShareRefused` (not busy) a message that is not the member's tenant or fails `topic.Valid` 1024, `$SYS` or QoS, and one the member's grants do not let it read (`canRead`, the same read check as mochi's per-delivery ACL). Otherwise it builds the PUBLISH for the member's shared subscription alone, as mochi's publishToClient would: namespaced topic, QoS min(published, granted, server max), retain flag only for a 5.0 subscription with Retain As Published, the subscription's identifier, message expiry from `PublishedAt` (now for QoS 0; an expired message is finished at once, nobody owed), origin the publisher's namespaced ID, protocol version (mochi expires inflight by it); never tagged. The session's writer (`shareOut`, one goroutine per session with memberships, ended at the session's end or its last leave) waits for the current connection's CONNACK (5 s, `connackWait`) and, for QoS 1 and 2, for room again (`shareTarget`/`outboundRoom`, polled every 20 ms, blocking only this writer: what was free at enqueue may be gone), takes the packet ID with `NextPacketID` (`claimID`: a delivery the books still hold under that ID was lost from mochi's map by a client PUBLISH reusing the ID, so a log delivery there is pinned and replayed as `onQosPublish` does, and a QoS2Out entry there goes), then QoS 1: registers it in `shPend[nsID][packet ID]` until the PUBACK (a stale one under the ID goes back to its group); QoS 2 (`pinShare`, ruling R39): writes `QoS2Out[packet ID] = {Seq 0, PUBLISH, Shared: log seq}` to a tracked session's record (`persistNow`; on failure nothing is sent, the message goes back to its group and the client is stopped; the pin counts only once a written record had it, `savedGen` at or past the insert's gen, because `persist` reports success without writing for a session whose last record is in: a pin made after that record goes back to its group, one the last record holds stays for the resume), then acks the group's message: the delivery is the session's [MQTT-4.8.2-4], and no other member gets it even if the session ends [MQTT-4.8.2-5]. An untracked session ends with its connection, so its QoS 2 is acked at once and dropped with it. Then it puts it in mochi's inflight map (so a takeover on this node resends it), pins a tracked session whose map it filled (`pinIfFull`, as an inbound QoS 2 reservation), and writes it with `cl.WritePacket` (OnPacketEncode strips the tenant as for any PUBLISH). A client that stops reading holds only its own writer. The writer re-checks, after `NextPacketID` and before `claimID`, that the session still has the connection it chose; if not it starts again with the current one, so a stale writer never clears the books (which the new connection uses) under an ID of the old connection. After the write, a QoS 1 or 2 delivery checks that the session still has that connection (`followShare`): a same-node takeover clones the old connection's inflight map and clears it, so an entry set on the old connection after the clone is in neither, and a takeover is not a resume from the record. When the session has moved, the writer first waits for the current connection's CONNACK (mochi replaces its inflight map until then, and has resent what it cloned by then; a wait that runs out reads the session again), deletes the orphan from every connection it passed that was taken over, and stops when a QoS 1 delivery is no longer the session's (`stillShared`: its pending entry `d` was given back or finished). An entry under the same ID that is this delivery (`isOwnShare`: untagged, and the QoS 2 pin under the ID is this message, at PUBLISH or PUBREL; or the QoS 1 pending entry is `d` and the entry carries the same message) was cloned and resent by mochi: left alone, so a delivery at PUBREL is never sent as a PUBLISH again. Otherwise the packet goes into the current connection's inflight map (a fresh packet ID if that connection already gave the ID to another delivery, `renumberShare`), a QoS 2 pin under the ID it goes out under is written to the record first (`repinShare`, `persistNow`), and it is written with DUP. Test seam `shareAfterWrite` runs right after the write. A QoS 1 write that fails on a closed connection gives the message back (inflight entry removed, send quota restored as mochi's own rollback does); a QoS 2 one stays in the inflight map and the record for the resume. One over the client's Maximum Packet Size is finished in OnPacketEncode (`discardOversized`: out of the inflight map and the record, the group's message done once); a QoS 0 one, or another packet mochi refuses to encode (a `packets.Code` error, `encodeFailed`), is dropped. Any other write error is the network's: the connection is lost even while mochi still reports it open (its reader has not read the peer's end yet, or Stop closed the socket and has not cancelled the client), so `shareWriteFailed` stops the client and handles the message as on a closed connection. Taking such an error for an encoding failure used to ack a QoS 1 message no member had received. The send quota is spent only for a new inflight entry, as mochi does. QoS 0: done after the write.
- Completion: QoS 1: OnPacketRead's PUBACK finishes the delivery (`shareAcked`) and the group's message is acked then. QoS 2 goes through the session's own machinery: `onPubrec` moves its QoS2Out entry to PUBREL (record written before mochi sends the PUBREL, R37), `onAck` deletes it at the PUBCOMP (marking nothing done: Seq 0 is not the session's log message). A resume on any node (`loadSession`'s Seq 0 branch, `sharedResend`, with the message read back from the log by `Shared`: `resendSeqs` lists pinned sequences apart from the session's own, and `fetchLogs` reads each pinned one with `cluster.Log.Get`, ruling R40, so a pin far below the session's own QoS 2 does not widen the ranged read of those on the CONNECT path) puts its PUBREL, or its PUBLISH untagged with the same packet ID (mochi resends it with DUP), in the offline client; no cursor, skip or flip floor; a message gone from the log or expired is dropped. `windowFull` counts Seq 0 entries against the Receive Maximum. OnQosDropped (mochi expired the inflight entry) finishes a QoS 1 delivery and removes a QoS 2 one from the record, only for the connection serving the session: a same-node takeover clones the inflight map and then clears the old connection's, firing OnQosDropped for every entry, which must not finish deliveries the new connection carries; a CONNACK prune of an inherited delivery the grants no longer allow (`prunedDelivery`) gives a QoS 1 one back and drops a QoS 2 one.
- The replay's window (`windowFull`) counts the session's shared deliveries in flight and queued (`sharedOutstanding`) against the Receive Maximum.
- Locks: `shMu` guards memberships, deliveries and writers and is never held across a Shared call or a write; deliver takes `sessMu`, `shMu` and the injection gate briefly, one at a time.
- QoS 0 for a group comes only from the queue group: the node's QoS 0 publishes (network clients, the host's inline client, wills) already go to `Router.Publish`, and the queue connection has no NoEcho, so a member on the publishing node can be picked (R5).
- Counters for tests: `sharedSent`, `sharedDone`, `sharedLost`, `shareErrors`; `sharedOf(nsID)` lists memberships, `pendingShares(nsID)` counts deliveries in flight.
- Known gaps: a group whose members all left keeps its consumer (and its place in the log) until the log's MaxAge passes with nobody pulling, so a new member of a group nobody held for a while can get messages published meanwhile; there is no cell-wide count of a group's members. A message a node handed to a member is redelivered only after the consumer's AckWait (30 s) when that node dies. The tenant's `$SYS` stats are per node and never routed, so a shared subscription to `$SYS` gets nothing in cluster mode. A resent shared QoS 2 PUBLISH is rebuilt from the log message: it keeps topic, payload, properties and origin, but not the subscription identifier or a Retain As Published flag of the first send.

## Admin reactions (admin.go)

Called by the host when keys, roles or tenants change; `events.NewReactor` drives the first three from keysmith and warden plugin hooks. Each bumps `Broker.changes` (an atomic counter a CONNECT compares, see OnConnectAuthenticate), then copies the matching states under the registry read lock and works on them after releasing it; a PermLoader call never runs under the registry lock. Work runs in the caller's goroutine. Before Start and after Stop they do nothing.

- `DisconnectPrincipal(principalID string, code packets.Code) int`: disconnects every live connection whose identity's `PrincipalID` equals principalID (5.0 clients get a DISCONNECT with code) and returns the count. Principal IDs must be unique across tenants (keysmith key IDs are TypeIDs).
- `ExpirePrincipal(principalID string, connectedBefore, at time.Time) int`: every live connection of the principal with `connectedAt` before `connectedBefore` gets `Identity.ExpiresAt = min(existing, at)` (under `reloadMu`) and its expiry timer set again; when it fires, the client is disconnected with 0xA0 like any expired credentials. Returns how many it shortened. Bumps `changes`, so a CONNECT in flight authorizes again. The reactor calls it for a key rotated with a grace window.
- `ReloadRole(ctx, roleID)`: reloads every live connection whose current grants came from roleID (the roleIDs its last Load returned).
- `ReloadPrincipal(ctx, principalID)`: reloads every live connection of that principal.
- A reload holds the state's `reloadMu`, calls `Perms.Load` with the stored identity and current tenant snapshot, compiles with the connection's raw client ID and CONNECT username, swaps the grants in, then prunes the subscriptions the new grants no longer allow: `Topics.Unsubscribe`, `cl.State.Subscriptions.Delete`, `Info.Subscriptions` decremented, and the badger hook's `OnUnsubscribed`, like an UNSUBSCRIBE without the UNSUBACK. A subscription survives exactly when a new SUBSCRIBE for it would pass (`Broker.canRead`, shared with OnACLCheck; the tenant's own `$SYS` always survives). Load errors: see PermLoader.
- Reload retries: a reload whose Load fails on an outage starts one retry loop per connection (`retryReload`), unless one is pending. It waits `retryBase` (1 s), doubling up to `retryMax` (30 s), and retries under `reloadMu` until a load works or `retryWindow` (2 min) has passed since the first failure; then the client is disconnected with 0x88 so it authorizes again on reconnect. A later reload that succeeds (or refuses) ends the pending loop (`st.retryStop` closed), and so does dropping the state (remove, sweep, takeover). `Stop` closes `retryQuit` (which also cancels a Load in flight) and waits for every loop before disconnecting clients; no loop starts after that. The three durations are unexported fields tests shorten; `pendingRetries` counts live loops.
- `disconnect` never lets the DISCONNECT write gate the close: the write runs in its own goroutine, and after `disconnectWait` (1 s) the client is stopped anyway, which closes the connection and fails a stuck write. Mochi's DisconnectClient writes before it stops the client and a write has no deadline, so a client that stops reading (while its own packets keep extending its keepalive) would otherwise block DisconnectPrincipal, UpdateTenant, a 0x87 reload and the admin call behind them. Shutdown disconnects clients in parallel for the same reason.
- `UpdateTenant(t *tenant.Tenant)`: stores a copy of t as the tenant snapshot of every live connection of t.ID, so OnPublish uses its limits from the next message; if `!t.Enabled` those connections are disconnected with 0x98. Call it after the tenant is stored and the resolver cache cleared (service.Tenants.Update does both), so a CONNECT that authorizes again reads the new tenant. With `Cluster.Control` it publishes the change and every node applies it on receipt (see Control bus).
- Pruning a session (reconnect) also drops queued PUBLISH inflights outside the grants: `Inflight.Delete`, `IncreaseSendQuota`, `Info.Inflight` decremented, badger `OnQosDropped`. Mochi v2.7.9 already deletes a session's stored inflights on every takeover (the old client's `ClearInflights`), so the storage call matters only if that changes.

## Admin operations (admin.go)

For the host's admin API (the API checks the caller's permissions and limits first; the broker checks none). Each takes a Tether tenant ID and client IDs and topics as the tenant's devices see them, namespaces them itself, and never lists or touches another tenant's clients, sessions or retained messages. A tenant ID that is not a canonical tenant TypeID (`id.ParseTenantID` and `String()` round-trips), an empty client ID or one with NUL, and a topic failing `topic.Valid` (with `MaxTopicLength`) are `tether.ErrInvalidInput`; the two listings return nil instead. None holds the registry lock across a mochi call.

- `ClientInfo{ClientID, Username, DeviceID, Remote string; Connected bool; ProtocolVersion byte; Subscriptions []string; ConnectedAt time.Time; SessionExpiry uint32}` (json snake_case; ConnectedAt omitzero). `RetainedInfo{Topic string; Size int; QoS byte}`.
- `Clients(tenantID) []ClientInfo`: cluster mode adds every session of the tenant in the cell that this node does not have (`clusterClients`, `Sessions.Entries` with a 5 s bound): from its record, Connected when a node owns it and `DisconnectedAt` is zero (a session kept for a delayed will, or a dead node's, is not connected; no Remote, no ConnectedAt); if the cell cannot be read only this node's are listed. Otherwise mochi's `Clients.GetAll()` (open connections and kept sessions of disconnected persistent clients) filtered to the tenant's `<tenant>/` prefix, inline client excluded, sorted by client ID; subscriptions un-namespaced and sorted. An open connection's Username, DeviceID, ConnectedAt and SessionExpiry come from its state; an offline session gets Username and SessionExpiry from mochi's client (read only once it is closed, since mochi changes them while open), and Remote is whatever mochi kept (empty after a restore).
- `Kick(tenantID, clientID) error`: the bounded `disconnect` with 0x98. No open connection (offline session included) or not started: `tether.ErrNotFound`. The session stays. With `Cluster.Control`, a connection another node serves is kicked by that node and Kick returns once the record shows it gone (see Control bus).
- `DeleteSession(tenantID, clientID) error`: `registry.beginDelete` sets a tombstone on the namespaced ID (a CONNECT for it is refused with 0x88 until the delete returns) and fails with `tether.ErrConflict` when another delete of it runs or another connection for it has already registered (it may be about to inherit the session). An open connection is disconnected (0x98) and DeleteSession waits up to `endWait` (`sessionEndWait`, 2 s; tests shorten it) for `ended`, so badger's OnDisconnect write is done. If the wait runs out, a connection still open is `ErrConflict`; a closed one (mochi skipped its OnDisconnect after a failed CONNACK write, a ghost) is deleted anyway. A session that ends with its connection (5.0 expiry 0, 3.1.1 clean; `endsWithConnection`, mochi's own rule) whose connection had closed before the call is `ErrNotFound` once `ended` is in, even while mochi still lists it: mochi removes it only after every OnDisconnect, and the same DELETE after a kick used to answer 404 or 204 by timing (`TestDeleteSessionOfEndedCleanSessionNotFound` holds mochi between the two with a hook; the API's `TestClientsAndStats` got 204 on CI). Then, unless mochi already removed the session (a clean session this delete disconnected) or holds another client under the ID (`ErrConflict`), `purgeSession`: `unsubscribe` everything (the routine pruning uses: topic index, session, `Info.Subscriptions`, badger `OnUnsubscribed`), `cl.ClearInflights()` (fires `OnQosDropped` on every hook), `Clients.Delete` if mochi still maps the ID to that client, badger `OnClientExpired`. The session does not come back after a restart. `beforePurge` (unexported, tests only) runs just before the purge. No session or not started: `tether.ErrNotFound`. A 5.0 delayed will mochi already queued is still sent. Cluster mode (ruling R7, `deleteClusterSession`): the client ID must pass `subject.CheckClientID`; the same tombstone; a session this node serves is marked deleting, disconnected (0x98) and waited for (its end evicts and writes nothing); a leftover closed local session is evicted; then `Sessions.Get`: absent is `ErrNotFound` (nil if a local session was just removed), owned by another node is deleted by that node over the control bus when there is one (see Control bus), else `ErrConflict` naming the node; otherwise `Sessions.Delete` at the revision read (a lost race is `ErrConflict`).
- `Retained(tenantID, filter) []RetainedInfo`: `Topics.Messages` on the namespaced filter, un-namespaced and re-checked with `topic.Match`, sorted by topic. A leading wildcard matches no `$` topic, so `#` never lists the tenant's `$SYS`; `$SYS/#` does. Shared filters match nothing. Cluster mode: the cell's messages, from `Retained.Load` (5 s bound, `retainedAdminWait`), `$SYS` and invalid entries skipped, same matching; if the store cannot be read it logs at Warn and lists this node's cache as above.
- `DeleteRetained(tenantID, topic) error`: refuses `$SYS` names in any casing; `tether.ErrNotFound` when nothing is retained there (or not started); otherwise an inline publish of an empty retained message, which makes mochi delete it and call badger's `OnRetainMessage(-1)`. Subscribers receive the empty message, as with any MQTT clearing. Cluster mode (`clusterDeleteRetained`): `subject.CheckTopic`; the topic counts as retained when this node's loaded cache holds it, else when `Retained.Load` finds it (an error is returned wrapped); then `storeRetained` (cache and store, error returned, no background retry), then the empty publish, which the hook routes with its retain flag taken off.
- `Publish(ctx, tenantID, topic, payload, qos, retain) error`: ctx error first; topic must pass `topic.Valid` and not be under `$SYS` or `$share` in any casing (any other `$` name is a tenant topic, as over MQTT); qos 0 or 1, else `ErrInvalidInput`; not started: `tether.ErrConflict`. Inline publish of a copy of payload: no ACL check, no rate limit, not counted in (deliveries count out). Mochi takes an inline publish as received at QoS 0 and delivers at min(qos, subscription QoS); every delivery still passes OnACLCheck. Cluster mode: the topic must also pass `subject.CheckTopic` (1024 bytes), and a QoS 1 publish is appended to the log and waited for instead (ctx bounds it; its error is returned), then delivered by every node's reader. A retained one is written to the cell's retained store under ctx (QoS 0: before the live publish, which is skipped when the write fails; QoS 1: after the commit), and that error is returned.
- `DevicePublish(...)`: the same, for a message a device sent over HTTP: on success it also counts as a message in for the tenant (`Stats.MessagesIn`, `$SYS/messages/received`, `Metrics.MessageIn`). The caller has checked grants and spent the rate budget.

## Session expiry (expiry.go)

Mochi expires a closed 5.0 session after its `Props.SessionExpiryInterval`, but a 3.1.1 session only after the broker's cap. The `$SYS` goroutine also runs `expireSessions` every second (`sessionSweepInterval`): an offline 3.1.1 persistent session whose flagged `Props.SessionExpiryInterval` has run out since `StopTime` is purged like DeleteSession does (`beginDelete` tombstone, wait for `ended` or skip, `purgeSession`). Sessions restored from storage carry the property, so they expire too. `Clients` reports a 3.1.1 offline session's expiry from the same property. Cluster mode runs no sweep: mochi holds no offline session, and the key's TTL (the session's expiry, set by the last record write) ends a 3.1.1 session in the cell like a 5.0 one.

## Tenant $SYS (sys.go)

Every 10 s (`Broker.sysInterval`, unexported; tests shorten it before Start) a goroutine started by Start publishes, through mochi's inline client (`Server.Publish`, QoS 0, not retained), for each tenant with at least one open connection: `$SYS/<tenant>/clients/connected`, `.../messages/received`, `.../messages/sent`, `.../subscriptions/count`, `.../retained/count`, decimal payloads from `Stats`. Clients subscribe to `$SYS/#` (namespaced to `$SYS/<tenant>/#`) and receive `$SYS/clients/connected` and so on. Stop ends the publisher before it drains mochi. Mochi's own `$SYS/broker/...` (retained, every second) stays: no tenant filter can match it and OnACLCheck denies it to every network client.

## Mochi v2.7.9 workarounds

- `Server.Close` can deadlock: `Clients.GetByListener` read-locks twice, so a client added or deleted in between blocks it forever. `Stop` closes the listeners with a no-op closer, disconnects every client and waits for `Listeners.ClientsWg` before calling `Close`.
- When writing the success CONNACK or resending inflight messages fails, attachClient returns without OnDisconnect. When a tenant hits its connection limit, the hook sweeps that tenant's closed connections (`registry.sweepClosed`), releases their slots and retries. A reconnect with the same client ID also drops a closed previous owner (registry `bind`). A live connection's slot is never released by either.
