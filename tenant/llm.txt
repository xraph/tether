# tether/tenant

Import: github.com/xraph/tether/tenant

Tenant model and store interface. Imports only `id`, so the root package can import it without a cycle.

- `Tenant{ID id.TenantID, AppID, ExternalID, Name string, Enabled bool, Limits Limits, CreatedAt, UpdatedAt time.Time}`. The `(AppID, ExternalID)` pair is unique: it maps a tenant to the host application's own identifier.
- `Limits{MaxConnections int, MessagesPerSecond float64, Burst int, MaxSessionExpiry time.Duration, MaxSessions int}`. Zero means "use the broker default", except `MaxConnections` and `MaxSessions`, where zero means unlimited.
- `MaxSessions` caps the tenant's sessions on one node: open connections plus kept offline persistent sessions. The broker checks it at CONNECT for a client ID with no session yet (0x97; 3.1.1 server unavailable); a client returning to its own session always may. Plain value types only: stores persist it as JSON.
- `MaxSessionExpiry` lowers the broker's session expiry cap for the tenant (whole seconds; zero is the broker's cap; a positive value under one second is invalid, because it would round to zero and end every session at disconnect). The broker enforces it at CONNECT: a 5.0 request above it is shortened and the CONNACK says so, a 3.1.1 persistent session gets it as its expiry, and a DISCONNECT cannot raise past it.
- `MaxConnections` counts the tenant's connections on every node of a cell that has a load reporter (`Cluster.Load`): a CONNECT is refused (0x97, 3.1.1 server unavailable) when the connections here plus the other nodes' latest reported ones reach the limit. The reports are up to one load interval old, so nodes that accept at the same moment can overshoot briefly. A client ID reconnecting on the node that holds it (a takeover) needs no second slot. Without a cell, or without `Cluster.Load`, it counts the one node. `MaxSessions` stays per node.
- `MessagesPerSecond` and `Burst` are one budget per tenant, shared by all of the tenant's connections (not per connection). Outside a cell it is per broker node. In a cell with `Cluster.Load` each node spends a share of it, recomputed every 10 s: its connections over the tenant's connections in the cell, or one slice per live node when it holds none of them (the HTTP publish endpoint). The rate and the burst are both scaled (burst rounds up, at least 1), and the shares may briefly sum above 1. The broker has no default rate, so a zero rate is unlimited; a zero burst is the rate rounded up, at least 1.
- `ListFilter{Limit, Offset int}`: Limit 0 is no limit, negative values are invalid input.
- `Limits.Validate()` refuses a negative limit and a `MaxSessionExpiry` above zero but under one second. `(*Tenant).Validate()` checks nil, a zero ID and then `Limits.Validate()`, so every store refuses bad limits on Create and Update. `(*Tenant).Validate()`, `Limits.Validate()` and `ListFilter.Validate()` return a plain error naming the problem (nil tenant, zero ID, bad limits, negative limit or offset). They are not tether sentinels, because this package must not import the root package: a store wraps the result once with `tether.ErrInvalidInput`.
- `Store`: `CreateTenant`, `GetTenant`, `GetTenantByExternal`, `UpdateTenant`, `DeleteTenant`, `ListTenants`.

Contract (every backend passes `store/storetest`):
- Missing record: error wrapping `tether.ErrNotFound` (Get, GetByExternal, Update, Delete). Duplicate ID or `(AppID, ExternalID)`, on Create or on Update moving onto another tenant's pair: `tether.ErrConflict`. Nil record or nil ID: `tether.ErrInvalidInput`.
- Create sets `CreatedAt`/`UpdatedAt` on the caller's struct when zero and normalises set ones to UTC at microsecond precision. Update keeps the stored `CreatedAt`, sets `UpdatedAt` to now, or to a microsecond past the stored one when that is not before now (so it grows with every write in write order, whatever the writers' clocks; the broker orders a cell's tenant snapshots by it), and writes both back to the caller's struct.
- `DeleteTenant` does not cascade. The service layer refuses to delete a tenant that still has devices.
- `ListTenants` order is `CreatedAt` ascending, then ID.
