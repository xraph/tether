# tether/cluster

Import: github.com/xraph/tether/cluster

Runs Tether broker nodes as one cell over NATS and JetStream. This package holds the configuration, the NATS connection (embedded or external), the stream and bucket provisioning, the session store and the sentinel errors. The QoS 1/2 log (log.go, reader.go, replay.go) sits on `*Conn` too. The QoS 0 router (route.go, dedup.go) sits on `*Conn` too, and so do the membership service (members.go), the retained store (retained.go), the control bus (control.go) and the shared subscription groups (shared.go).

## Config

`Config{Enabled, NodeID, Cell, Mode, URLs, Embedded, Heartbeat, Lease, Credentials, Replicas, NoDiscovery, LogMaxAge}` with snake_case yaml and json tags (`no_discovery`, `log_max_age`). `EmbeddedConfig{ServerName, ClusterName, Listen, ClusterListen, Routes, StoreDir, User, Password, Insecure}` (`user`, `password`, `insecure`). `DefaultConfig()`: disabled, mode "embedded", heartbeat 2 s, lease 24 s (ruling R48: Lease/2 = 12 s has to outlast a nats-server 2.15 JetStream election of 4 to 9 s, or losing one server fences the cell), LogMaxAge `DefaultLogMaxAge` (7 days). `LogAge()` is LogMaxAge, or the default when it is 0: the MaxAge to pass Provision (ruling R44), how long an offline session's QoS 1/2 messages wait whatever its session expiry. `Validate()` returns nil when Enabled is false. When enabled: NodeID is 1 to 64 bytes of `[-_a-zA-Z0-9]` (it becomes a KV key and a subject token), Cell matches `^[a-z0-9]{1,16}$`, Mode is "embedded" or "external", external needs a URL, embedded needs `Embedded.StoreDir`, `Embedded.Routes` needs `ClusterName`, and `ClusterName` or `Routes` needs `ClusterListen`, Lease must exceed 2 x Heartbeat, Replicas is 0 to 3, LogMaxAge is not negative. Embedded `User` and `Password` go together. Ruling R43: an embedded `Listen`, or a `ClusterListen` while `ClusterName` is set, whose host is not loopback (`localhost`, 127.0.0.0/8, ::1; an empty host binds every interface and an unparsable address counts as open) is refused unless `User` and `Password` are set or `Insecure` is true, because anyone reaching the port could read every tenant's traffic or join the cell as a route.

`EmbeddedConfig{ServerName, ClusterName, Listen, ClusterListen, Routes, StoreDir}`. ServerName defaults to NodeID, Listen to "127.0.0.1:-1". List every other server in Routes: JetStream sizes its meta group from the route count, so a node given one seed route may elect a leader alone.

Names (all derive from Cell): `LogStream()` TETHER_LOG_<CELL>, `ControlStream()` TETHER_CTL_<CELL>, `SessionsBucket()` tether-sessions-<cell>, `RetainedBucket()` tether-retained-<cell>, `MembersBucket()` tether-members-<cell>. The KV backing streams are `KV_<bucket>`.

## Connect

`Connect(ctx, cfg, *slog.Logger) (*Conn, error)`. A nil logger discards. Embedded mode starts an in-process nats-server with JetStream (cluster routes when given) and connects in-process. External mode dials `URLs` (with the `Credentials` file when set). With `Embedded.User` set, the embedded server requires that user and password of every client (`server.Options.Username/Password`) and route (`ClusterOpts.Username/Password`; each route URL without user info gets them, so every server of the cell must be given the same pair), and both of the node's connections send them (`nats.UserInfo`). It returns once JetStream answers, or fails with an error wrapping `ErrUnavailable` when ctx ends (30 s when ctx has no deadline). The nodes of an embedded cluster only get JetStream once enough peers are up, so start them together; a node started alone waits.

The connection uses `nats.NoEcho()`: a node never receives its own core NATS publishes. The router relies on it. Reconnect is unlimited, 500 ms apart.

A second connection, without NoEcho, carries the QoS 0 queue groups of shared subscriptions (ruling R5), so a group member on the publishing node can win the queue pick of that node's own publish. It is unexported (`queueConn()`), opened on first use from the same address and options (credentials, `InProcessServer` in embedded mode, NoDiscovery) with the name `tether-<node>-shared`, and drained by `Close` before the main connection; after Close it never opens.

`Config.NoDiscovery` adds `nats.IgnoreDiscoveredServers()` and `nats.DontRandomize()`: the connection uses only the URLs it was given, in order, and never the ones a NATS cluster advertises, so when its server goes away it waits for that server instead of failing over. Production leaves it off. A node that reaches NATS through a proxy sets it (the fault proxy in tests; without it nats.go reconnects around the proxy, ruling R17). With it on, the automatic replica count (`Replicas()`) only sees the given URLs, so set `Replicas`.

- `(*Conn).JS() jetstream.JetStream`, `NC() *nats.Conn`.
- `Healthy(ctx) error`: connected and JetStream answers; the error wraps ErrUnavailable.
- `MaxPayload() int64`: the server's max_payload, headers included (0 before the connection has heard from a server). Embedded mode sets it to `EmbeddedMaxPayload` (4 MiB: a 1 MiB MQTT packet fits as a retained value, base64 in JSON); external servers keep theirs (nats-server's default is 1 MiB). The broker lowers its Maximum Packet Size to fit it.
- `Close()`: drains the connection, then shuts down the embedded server. Idempotent.
- `Replicas() int`: the replica count Provision uses. `Config.Replicas` when set. Otherwise min(3, servers): embedded mode counts 1 + len(Routes); external mode counts max(len(URLs), 1 + servers the client discovered) when the server reports a cluster name, else 1. Both can count too few: a server that advertises nothing (no_advertise, or one URL in front of a load balancer) makes a cluster of any size count as 1, and an embedded node given only a seed route counts 2. Connect logs a Warn when the count is automatic, under 3 and the NATS is clustered (an embedded cluster name, or a server reporting one): set Replicas then. Provision with automatic replicas never lowers a stream or bucket that already has more (`keepReplicas` reads the stream, `KV_<bucket>` for a bucket, bounded at 2 s; one it cannot read gets the count), so the last node to start cannot scale the cell down.

## Provision

`Provision(ctx, c, cfg, maxSessionExpiry) error` creates or updates, so every node can call it on start:

- TETHER_LOG_<CELL>: subjects `d.>`, file storage, MaxAge = maxSessionExpiry (0 = unlimited), duplicate window 2 min.
- TETHER_CTL_<CELL>: subjects `ctl.>`, file storage, MaxAge 1 h.
- sessions bucket: history 1, limit markers, LimitMarkerTTL 1 min.
- retained bucket: history 1, limit markers, LimitMarkerTTL 1 min.
- members bucket: history 1.

All with `Conn.Replicas()` replicas (automatic replicas keep a higher count an existing one has, above). Pass `cfg.LogAge()` as maxSessionExpiry (the extension does). Each create or update is one attempt bounded at 1 s, doubling to 8 s; placement errors that clear while a fresh cluster's meta group fills (JetStream API codes 10005, 10008) and attempts nobody answered (deadline, `nats.ErrTimeout`, no responders, while ctx runs) are retried until ctx ends. The unanswered case is real: when every node of a fresh multi-server cell provisions at once, the meta leader leaves concurrent creates of the same stream or bucket unanswered, and without the bound each node waited out its whole ctx (`TestProvisionConcurrentFresh`). Sending a create again is harmless. The subjects are not namespaced by cell, so two cells cannot share a NATS account.

## Errors

`ErrLostCAS` (JetStream 10071 and 10164 both mean this; Sessions maps both, and the returned error also wraps the `*jetstream.APIError`), `ErrFenced`, `ErrUnavailable`, `ErrTooLarge` (a write over `Conn.MaxPayload`, nats.go's `ErrMaxPayload` before anything is sent, or JetStream 10054; Log, Retained and Sessions map it, and the error also wraps `tether.ErrInvalidInput`: sending it again never helps). Messages start `tether/cluster: `.

## Sessions

One KV key per MQTT session in the sessions bucket, key `subject.SessionKey(tenant, clientID)`, value a JSON `SessionRecord{Owner, Epoch, Clean, ProtocolVersion, Username, DeviceID, ExpirySeconds, Subscriptions []SubRecord, Cursor, Will *WillRecord, QoS2In map[uint16]string, QoS2Out map[uint16]OutRecord, DoneThrough, Pending []uint64, QoS2Done []uint64, DisconnectedAt}`. The broker's cursor fields (Task 9): `DoneThrough` (every tenant message up to it was dealt with for the session except those in `Pending`), `Pending []uint64` (log sequences of the outbound QoS 1/2 deliveries in flight, bounded by the inflight window), `QoS2Done []uint64` (completed outbound QoS 2 above `DoneThrough`; their packet IDs may be reused, so they are not in `QoS2Out`). `OutRecord{Seq, State, Shared}`: a `QoS2Out` entry with `Seq` 0 is a shared subscription's QoS 2 delivery pinned to the session (rulings R37, R39); `Shared` (json `shared`, omitted when 0) is its message's log sequence, so a resume sends that message again under the same packet ID, or its PUBREL, and the cursor is not involved. `Cursor` is at most `DoneThrough`. `WillRecord.Props` is a `Props` (props.go): `User []UserProperty` (ordered, duplicate keys kept), `ContentType`, `ResponseTopic`, `CorrelationData`, `MessageExpiry` (seconds, 0 = none), `PayloadFormat *byte` (nil = absent). `Props.IsZero()` backs `omitzero`.

`NewSessions(c *Conn, cfg Config) *Sessions` (the bucket must exist, so Provision first). Every method checks the client ID with `subject.CheckClientID` and a non-empty tenant, and returns an error wrapping `tether.ErrInvalidInput` otherwise; no "" key is ever written. A write that loses wraps `ErrLostCAS`; a NATS timeout or no responders wraps `ErrUnavailable`. A call without a context deadline gets 10 s. A write whose context ends gives the key's per-key lock back without knowing whether its publish landed; it may commit later and move the revision, so the next write of the key loses its CAS to the caller's own write: read the key (Get, Owner and Epoch) before treating a lost CAS as a takeover (the broker does). `OnLostCAS(fn func())`: fn runs once for every write that loses its CAS (Acquire, Update, Expire, Delete; an Acquire's own internal retry counts), before the call returns or retries. For metrics: quick, concurrent-safe; nil removes it; one observer per Sessions.

- `Acquire(ctx, tenant, clientID, nodeID) (rec, rev, existed, err)`: read from the stream leader, then CAS the record with Owner = nodeID and Epoch + 1. Absent key: created at epoch 1. A key holding only a limit marker or purge marker reads as absent but the create must name the marker's revision (JetStream refuses expected sequence 0 while the marker lives, until `LimitMarkerTTL`); Acquire does that. `rec` is the record as it was, with the new owner and epoch. A lost CAS is returned, not retried, except one retry of a create that lost over a stale marker read.
- `AcquireWith(ctx, tenant, clientID, nodeID, build func(prev *SessionRecord) *SessionRecord) (rec, prev, rev, err)`: Acquire where build makes the record written from the previous one (nil when none lived); AcquireWith sets Owner and Epoch (previous + 1) on it and returns it, the previous record (nil when none) and the new revision. build must not change prev and may run twice. Acquire is AcquireWith with a copy of prev.
- `Update(ctx, tenant, clientID, rev, rec) (newRev, err)`: CAS, no TTL (this clears an earlier Expire).
- `Expire(ctx, tenant, clientID, rev, rec, ttl) (newRev, err)`: CAS like Update, as a raw publish to `$KV.<bucket>.<key>` with `Nats-TTL` (whole seconds, rounded up, min 1 s) and `Nats-Expected-Last-Subject-Sequence`. When it runs out the key becomes a limit marker; watchers see a purge with reason MaxAge.
- `Delete(ctx, tenant, clientID, rev) error`: CAS purge that leaves a marker for `LimitMarkerTTL`.
- `Get(ctx, tenant, clientID) (rec, rev, err)`: `tether.ErrNotFound` when absent, deleted or expired. Reads use the JetStream non-direct message get, so the stream leader answers and a node sees its own writes.
- `List(ctx, tenant) ([]*SessionRecord, error)`: a watcher pass over the tenant's keys, live ones only. `Entries(ctx, tenant) ([]SessionEntry, error)` is the same pass with `SessionEntry{Tenant, ClientID string; Record *SessionRecord; Revision uint64}`. `OwnedBy(ctx, nodeIDs ...string) ([]SessionEntry, error)`: one watcher pass over the whole bucket (every tenant), keeping the records whose Owner is one of nodeIDs (no ID or an empty one: ErrInvalidInput). The revisions are those the pass read, so a CAS from one loses if the key moved since. The broker's dead-node reclaim uses it.
- `WatchOwned(ctx, nodeID, fn func(tenant, clientID string, rec *SessionRecord, deleted bool)) (stop func(), err error)`: one watcher over every key. It tracks the sessions nodeID owns (from this Sessions' successful Acquire, Update and Expire, and from records the watch reads with Owner == nodeID) and calls fn once when one changes owner or epoch (rec is the new record), or is deleted, purged or expired (rec nil, deleted true), then forgets it. This Sessions' own writes and deletes never fire. It returns after the first pass over existing keys. fn runs on one goroutine. A watch that ends by itself (its subscription closed under it) is logged at Error and started again with backoff (ruling R26); `ready` is closed if the first pass never finished, and the new watch's first pass resyncs: a takeover it missed fires then, and an owned key the pass did not read (its marker gone) fires as deleted. Decisions compare revisions, with a write in flight parking the watch's event until the write's revision is known. stop is idempotent.
- One outstanding CAS per key per node: a keyed lock inside Sessions (entries freed when unused). JetStream refuses an expected-sequence write on a subject that has any write in flight (10164), so two writes of one key from one node must not overlap. A loser behind the lock meets an applied write (10071).

Internals worth knowing: `isLostCAS(err)` matches API error codes 10071 and 10164 and nats.go's `ErrKeyExists` and `ErrKeyRevisionMismatch`. `Sessions.afterRead` is a test hook that holds Acquire between its read and its write.

## Log

The cell's QoS 1 and 2 messages live in one JetStream stream, `Config.LogStream()`, subject `subject.Log(tenant, topic)` = `d.<tenant>.<enc topic>` (`$` topics stay under the plain tenant token). `Log` never creates the stream: Provision first. Everything that delivers a QoS 1/2 message to a session reads it through a `Reader` or `Replay`, so a tenant's order is the stream order.

`LogMessage{Seq, Tenant, Topic, Payload, QoS, Retain, Props, Origin, ClientID, PublishedAt}`. Tenant and topic are not headers: they come back from the subject through `subject.DecodeLog`, which is lossless. Headers: `Tether-QoS` (1 or 2), `Tether-Retain` ("1" when set), `Tether-Origin` (node ID, omitted when empty), `Tether-Client` (base64url client ID, omitted when empty), `Tether-Published-At` (unix nanoseconds), and the `Tether-Prop-*` headers of `Props`. Readers and Replay hand the same Payload and Props arrays to every caller on the node: do not modify them.

`NewLog(c *Conn, cfg Config) *Log` keeps a JetStream handle of its own for publishing, with a 30 s ack timeout so abandoned publishes free their bookkeeping.

- `Append(ctx, msg, msgID) (seq, dup, err)`: refuses with `tether.ErrInvalidInput`, before building a subject, an empty tenant, a topic over 1024 bytes (`subject.CheckTopic`), a QoS other than 1 or 2, and an Origin or msgID that is not a plain header value (no control characters, no space at either end). Async publish (`PublishMsgAsync`), waits for the ack future or ctx (10 s when ctx has no deadline). A non-empty msgID is `Nats-Msg-Id`: a repeat inside the 2 minute window returns the first sequence with `dup` true and stores nothing. `msg.Seq` is ignored; a zero PublishedAt becomes now. Unreachable JetStream, no ack in time and a closed connection wrap `ErrUnavailable`. When the publisher has 4000 acks outstanding Append waits and retries until ctx ends.
- `AppendAsync(ctx, msg, msgID) (*PendingAppend, error)`: Append in two steps. It checks like Append, sends, and returns at once; `(*PendingAppend).Wait(ctx) (seq, dup, err)` waits for the commit (10 s without a deadline; ErrUnavailable on no ack in time or an unreachable JetStream, after which the message may still have been stored, so send it again under the same msgID; a Wait that ends on its context can be called again). `(*PendingAppend).Settled() (bool, error)` says without waiting whether the append has its answer and, if so, the error Wait will return (nil for a commit); the answer is kept, so a later Wait returns it. Answers need not come in send order (nats.go republishes by itself after a 503, and a leader answers a duplicate message ID at once), so the broker does not read anything into the order. Wait and Settled are for one goroutine. Calls on one Log reach the stream in call order, so a caller that starts appends in order gets them committed in order. ctx bounds only the wait while the publisher has 4000 acks outstanding. Append is AppendAsync plus Wait.
- `OnAppend(fn func(time.Duration))`: fn observes every append that commits, called by `Wait` or `Settled`, whichever takes the ack first, with the time from the send (in AppendAsync) to then. Failed appends are not reported. For metrics: quick, concurrent-safe; nil removes it; one observer per Log (atomic pointer).
- `LogMessage.ClientID`: the publisher's client ID within its tenant ("" for a host publish), header `Tether-Client`, base64url (unpadded) so any client ID survives; the broker uses it for No Local.
- `Reader(tenant, fromSeq, fn) (*Reader, error)`: ordered consumer with exactly one filter `subject.LogTenantAll(tenant)`. fromSeq 0 = only messages appended from now (resolved to last sequence + 1 at creation, so a consumer recreated before its first message does not skip any); otherwise the first tenant message at or after fromSeq. The server consumer exists when Reader returns. fn runs on one goroutine; an fn error is logged at Warn and the reader goes on (one bad message must not stall a tenant); an entry that does not decode is logged at Warn and skipped. `Position()` (atomic) is the sequence of the last entry the reader is done with (fn returned, or skipped), starting at fromSeq-1 (or the log's last sequence for fromSeq 0), never going back. `Stop()` is idempotent and returns promptly even while NATS is unreachable: it waits only for an fn that is mid-message (a mutex held while fn runs), after which fn never runs again. The iterator stop and the server consumer delete happen in the background (the ordered consumer's recreate loop can take 20 s or more to notice). Do not call Stop from fn. `Done() <-chan struct{}` closes when the reader delivers nothing more and Position is final: after Stop once the loop has exited, and by itself when the reader ended because its consumer failed or stalled; a reader whose Done closed without a Stop delivers nothing more, so start a new one from `Position()+1` (the broker does). The consumer cleanup may still run when it closes. Position moves under the same mutex as fn, so it is final once Stop holds it.
- No silent stall (chaos finding CHAOS-2): nats.go's ordered consumer recreates itself inside `Next` and, by default, retries forever under the same consumer name. When the meta layer had placed that name on a server that then died (a create 4 ms after a kill -9, before the meta layer knew), every retry answers 10119 "consumer is offline", so the reader never ended, never delivered again and logged nothing. Now: (1) every ordered consumer of the log and the control bus sets `MaxResetAttempts` to `consumerResetAttempts` (1, stall.go): a failed recreate reaches `pump`, which returns the error (it no longer retries `Next`, which after a failed reset only reports the iterator closed); the reader logs it at Error (Warn for a closed connection), stops and closes Done, and the owner's new reader gets a new name, which the meta layer places on a live server. (2) A stall watch (`stallWatch`, stall.go) per reader: when the consumer has handed out nothing for `Log.stallAfter` (30 s; tests shorten it), no fn is running, and the tenant's last sequence in the log (`lastTenantSeq`, as Replay reads it) is above Position, the reader logs at Error, stops and closes Done. An idle reader that is caught up costs one such read per 30 s. A read that fails (NATS down) decides nothing: the watch then reads at every check, whatever the quiet time, until the stream answers, and counts that first answer as progress. So after an outage a reader gets a whole `stallAfter` from the moment the stream answers again (give or take one check interval) before it can be ended, and a reader catching up after a long outage is not ended for the outage. Checks run every stallAfter/4, jittered by a quarter, so readers started together do not ask together. `Log.resetAttempts` (tests, -1 = nats.go's endless loop) and `Log.stallAfter` are unexported.
- `Ping(ctx) error`: asks the log stream for its info, which only its leader answers (or, while it has none, a member that says so); nil means a leader answers, so an append can commit. No answer or no leader wraps ErrUnavailable; 10 s without a deadline. The broker's prober uses it to learn the log is back after an outage without sending appends into it (CHAOS-1).
- `Get(ctx, tenant, seq) (LogMessage, error)`: one message by sequence, from the stream leader (`GetMsg`); a sequence with no message, or another tenant's message, wraps `tether.ErrNotFound`; empty tenant or sequence 0 wraps ErrInvalidInput; 10 s without a deadline; unreachable wraps ErrUnavailable. For a few scattered sequences (the broker's pinned shared QoS 2 at resume, ruling R40); Replay reads a range.
- `Replay(ctx, tenant, fromSeq, toSeq, fn) error`: reads the tenant's messages in [fromSeq, toSeq]. The range is cut to the tenant's last message when the call starts (read with `GetLastMsgForSubject`), so a large toSeq does not wait for new messages; an empty range returns nil without a consumer. Calls for one tenant on one node share a consumer when the running one started at or below the newcomer's fromSeq and has not yet handed out a message with sequence fromSeq or more; otherwise the newcomer gets its own. Each call receives only its own range. fn runs on the consumer's goroutine (a slow fn slows calls that share it); an fn error ends that call alone with the error wrapped; when Replay returns fn is not running. ctx ends the call at once, also during an outage (a cancelled call gets no further fn calls); the consumer stops in the background, and is deleted, when no call uses it. A consumer that says it has caught up (pending 0) is double-checked against the tenant's last sequence before the calls waiting on it are ended, because a message appended after the server counted pending could fall in a later caller's range. A replay consumer is built like a Reader's (bounded recreate, `pump` returning the error): when it fails, the calls still waiting end with an error wrapping ErrUnavailable and the cause, and the broker retries them. Its stall watch needs no NATS call: it ends the waiting calls (ErrUnavailable, logged at Error) when nothing was handed out for `stallAfter` while a call's range still reaches past the last sequence handed out.
- `Log.consumers` (atomic) counts the server consumers the Log created, and `Log.heartbeat` sets the pull heartbeat (0 = nats.go default, 5 s); tests read and set them.

`Props` encoding (props.go, unexported `encode(nats.Header)` and `decode(nats.Header) error`): headers only for present properties. `Tether-Prop-User` is base64url (unpadded) of frames, per property uvarint(len key) key uvarint(len value) value, so order, duplicate keys, CR/LF and non-UTF-8 bytes survive. `-Content-Type`, `-Response-Topic` and `-Correlation-Data` are base64url of the raw bytes. `-Message-Expiry` and `-Payload-Format` are decimal numbers (the latter present means non-nil, so a pointer to 0 survives). A header that does not parse is an error from decode.

## Router

QoS 0 messages cross nodes by NATS subject interest, on core NATS (no JetStream). `NewRouter(c *Conn, nodeID string, deliver func(tenant, topic string, payload []byte, props Props, retain bool)) *Router`. Each node holds one core subscription set per distinct (tenant, filter) with local subscribers and publishes every message once; NATS delivers it to each node with interest. Local delivery stays with the broker: the connection is NoEcho, so a node never receives its own publishes. Two Routers in one test process need two `Connect` connections.

- `Subscribe(tenant, filter) error`: one reference. The first one subscribes `subject.QoS0Filters(tenant, filter)` (two subjects for a trailing `#`: the parent and `parent.>`), later ones only count. `Unsubscribe(tenant, filter) error`: drops one; the last unsubscribes. An Unsubscribe with no matching Subscribe returns an error wrapping `tether.ErrNotFound` and changes nothing.
- Validation: the filter goes through `subject.CheckTopic` and `topic.Valid(filter, true, 1024)`, and an empty tenant is refused. `$share/...` filters are refused (Shared carries them). All of these wrap `tether.ErrInvalidInput`, and nothing is ever subscribed for a refused filter. A NATS failure wraps `ErrUnavailable` when it is a connection or timeout error.
- `Publish(tenant, topic string, payload []byte, props Props, retain bool) error`: `subject.CheckTopic`, then `topic.Valid(topic, false, 1024)` (no wildcards, no NUL, not empty), then one `PublishMsg` on `subject.QoS0(tenant, topic)`. Headers: `Tether-Id` = `<node id>:<counter>` (the counter is atomic and starts at the clock reading at NewRouter, so a restarted node does not repeat ids inside the dedup window), the `Tether-Prop-*` headers of `Props` (`Props.encode`) and, for a retained publish, `Tether-Retain: 1` (the log's header name), which the receiver hands to deliver as `retain` (ruling R33b: a Retain As Published subscriber on another node sees the flag). It does not wait; a message nobody has interest in is dropped by NATS.
- Receiving: tenant and topic come from the subject through `subject.DecodeQoS0` (an undecodable subject is logged at Warn and dropped). Props come from `Props.decode`; a header that does not parse is logged at Warn and the message is delivered with empty Props. A message without `Tether-Id` (a publisher that is not a Tether node) is delivered without deduplication and logged at Debug.
- Dedup (dedup.go): a message that matches two of a node's subscriptions (`a/+` and `a/#` for `a/b`) arrives twice. The second is dropped by `Tether-Id` within 2 s. 16 shards of id -> first seen, each also keeping its ids in arrival order so expired ids fall off the front on every insert (no sweeper goroutine). Capped at 2^18 ids; at the cap the oldest go first, so a burst larger than that can let a duplicate through. Memory follows the message rate times 2 s.
- deliver runs on NATS dispatch goroutines, one per subscription. Order (ruling R19): the dedup claim and deliver run under a lock picked by the subject (64 stripes, FNV-1a), so calls for one topic never overlap and come in publish order even when several of the node's subscriptions match it (otherwise the goroutine that lost message N's claim could deliver N+1 while the winner was still delivering N). Calls for different topics can overlap. A slow deliver delays its subscription and the subjects sharing its stripe, and past the nats.go pending limits NATS drops (QoS 0 allows it). Keep it short: hand off to the broker's queues. payload and props belong to deliver.
- Locking: the router's map lock (`Router.mu`) guards the route table, `closed` and each route's pin count, and is never held across a NATS call. Each route has its own mutex that serializes that key's first subscribe and last unsubscribe, so concurrent Subscribe/Unsubscribe on one key keep refs and subscriptions in step while other keys proceed. A route is pinned while anyone holds or waits for it and removed when idle with no references; `unpin` takes `Router.mu` while still holding the route mutex (order: route mutex, then `Router.mu`), so refs cannot change between the idle check and the delete.
- `Close()`: unsubscribes everything, idempotent, does not close the Conn, and is not a barrier for deliver: a message NATS already handed to a dispatch goroutine can reach deliver briefly after Close returns. After it Subscribe, Unsubscribe and Publish return an error wrapping `ErrUnavailable`. A Subscribe racing Close never leaves a subscription behind (the route is marked dead under its mutex).

route_test.go (package cluster, `startRouteNodes` gives n nodes, each with its own connection, on a three-server cell; `ready(a, b)` waits for b's interest to reach a's server with a probe subscription, which routes keep in order) covers routing across nodes, overlap dedup over three filters, topic order through four overlapping filters with a slow deliver (`TestOverlapKeepsTopicOrder`, 2000 messages; it fails without the order lock), `a/#` matching `a`, the `$` rule, tenant isolation, refcounts, NoEcho, the Props and retain flag round trip, a foreign publisher, invalid input, Close, concurrent Subscribe/Unsubscribe and Close racing Subscribe under -race, and the dedup window and bounds with a fake clock.

## Members

`NewMembers(c *Conn, cfg Config) *Members` (the members bucket must exist: Provision first). Each node writes `{node_id, started_at, seq}` (snake_case JSON) under its own key (the node ID) in the members bucket every `Heartbeat`, with a plain `Put` (history 1), and watches every key. A renew succeeds when the KV put is acknowledged. A write times out after Lease/4, well under Lease/2, and the heartbeat goroutine and the monitor are separate, so a hung write cannot hold the fence back. Another write goes out every 250 ms (`renewRetry`, or Heartbeat if shorter) while the last one failed, or while the one outstanding has gone unanswered for more than twice the time the last acknowledged write took (250 ms at least), with at most two outstanding (`maxRenewsInFlight`), each bounded by Lease/4 (ruling R47). Whichever is acknowledged first renews, and the next write is due a Heartbeat after the one that renewed went out, whatever is still outstanding: a bucket that is slow but working (writes up to Lease/4) gets one write per Heartbeat and never fences the node. A failure of a write sent before the last one that renewed is stale and dropped, so it never reports a failure right after a renew. When the members bucket loses its leader, the writes sent to the old leader are swallowed without a reply (a stream member drops a publish it cannot lead), so with both slots taken the next write goes only when the first of them ends at Lease/4 (6 s by default); the node renews once that has happened and the bucket has a leader again, give or take a retry, well inside the 12 s fence. `Members.writes` counts writes sent (tests). Every duration is a local `time.Now()` reading compared with `time.Since`; KV timestamps are never used.

- `Start(ctx) error`: writes the first heartbeat, then starts the watch and waits until it has delivered the members that exist (the nil marker). ctx bounds Start only (10 s when it has no deadline); the goroutines run until Stop. A Stop during Start ends it. Once only. A missing bucket is an error that does not wrap ErrUnavailable; a timeout does.
- `Stop()`: idempotent; waits for the goroutines and for a callback that is running, and no callback runs after it returns. The node's key stays in the bucket (peers declare it dead after the lease), it is not deleted. Never call it from a callback.
- `OnFence(fn)`: once when no renew has succeeded for Lease/2. Checked every Heartbeat/4 (min 5 ms), so it fires within Lease/2 + one tick of the last renew, however the connection fails (blackholed, closed, JetStream down). `OnUnfence(fn)`: when a renew succeeds again after a fence. `Fenced() bool`.
- `OnPeerDead(fn func(nodeID string))`: once per peer that has not been seen for Lease + 2 s (`peerDeadMargin`, fixed; not configurable). "Seen" is the local receive time of a watch update with a higher revision (or a new started_at); a replayed update proves nothing. A peer heard from again is live again (logged, no callback) and can die a second time. A node never declares itself dead. Key deletions in the bucket are ignored, so the peer just ages out.
- While this node is fenced, or its watch has not shown its own heartbeat for a Lease, nobody is declared dead and every live peer's clock restarts each tick: a node that cannot see the cell must not call the cell dead, and gives its peers a full window once it sees again.
- A watch whose subscription closes under it (nats.go ends a KV watcher whose consumer it cannot recreate with a non-retryable error) is logged at Error and opened again with backoff (200 ms doubling to 5 s) until it works or Stop; the new first pass replays every key, which `observe` takes as replays. Before, the loop returned silently and the node never heard a peer again (CHAOS-2 audit).
- `Live() []string`: sorted IDs of this node and the peers not declared dead; nil while fenced. `IsLeaderFor(deadNode) bool`: this node is running, not fenced, is not deadNode, and has the lowest ID (byte order) among the live nodes other than deadNode.
- `Dead() []string`: sorted IDs of the peers this node declared dead and has not heard from since (what it last decided, fenced or not). The broker's sweep uses it to find dead nodes whose keys nobody settled.
- Callbacks run one at a time, in transition order, on one Members goroutine and never under a lock of Members. A slow callback delays the ones behind it and Stop; hand real work to your own goroutine. Register them before Start.
- Locking: one mutex guards the state; no NATS call is made while it is held.

## Retained

`NewRetained(c *Conn, cfg Config) *Retained` (the retained bucket must exist: Provision first). One key per tenant and topic, `subject.RetainedKey(tenant, topic)`: `<tenant>.<levels>`, or `==<tenant>.<levels>` when the first level starts with `$`, so an ordinary `#` filter of the tenant (`subject.RetainedKeyFilter`) never lists a `$SYS` key. The value is JSON `{payload, qos, props, origin, client_id, published_at}` (`Props` with its own JSON tags, user properties as an ordered slice, duplicates kept); tenant and topic come back from the key. Last write wins, no CAS. Safe for concurrent use.

Every method checks first: a topic over 1024 bytes (`subject.CheckTopic`), a topic that is not a valid MQTT topic name (`topic.Valid`: empty, `+`, `#`, NUL), an empty tenant and a QoS over 2 all wrap `tether.ErrInvalidInput`, and nothing is written, so no "" key exists. A NATS timeout or no responders wraps `ErrUnavailable`. A call without a context deadline gets 10 s.

- `Put(ctx, tenant, topic, msg LogMessage, expiry time.Duration) error`: stores Payload, QoS, Props, Origin, ClientID and PublishedAt (zero = now); Tenant, Topic, Seq and Retain of msg are ignored. An empty payload is a Delete. A positive expiry is a raw publish to `$KV.<bucket>.<key>` with `Nats-TTL` (whole seconds, rounded up, min 1 s, as `Sessions.Expire`); pass what is left of the MQTT 5 message expiry. When it runs out the key becomes a limit marker and watchers see a removal. A value over the server's max_payload fails with `ErrTooLarge`.
- `Check(msg LogMessage) error`: size only, nothing sent: an error wrapping `ErrTooLarge` (and `tether.ErrInvalidInput`) when Put would be refused as too large, nil when it fits or the payload is empty. The broker calls it before appending a retained publish, so one the store cannot hold is refused whole.
- `Delete(ctx, tenant, topic) error`: a purge (rollup) whose marker carries `Nats-TTL` of the bucket's `LimitMarkerTTL` (1 min), so markers do not pile up. Deleting an unset topic is not an error.
- `Load(ctx, tenant) ([]LogMessage, error)`: every retained message of the tenant, both key spaces, sorted by topic, through one watcher pass over `<tenant>.>` and `==<tenant>.>`. Each has Tenant, Topic and `Retain` set, and `Seq` = the key's revision (cell-wide, so of two readings of a topic the higher Seq is newer). Every write acknowledged before the call is in the result (the leader mark below), so set on node A then Load or Watch on node B right after sees it.
- Leader mark (`catchUp`): a KV watcher's consumer is R1 and nats-server places it on any active peer, possibly a follower a few ms behind, which delivers what it lacks later as updates. So after the watcher exists, Load and every Watch pass ask the stream leader for the newest revision under the two filters (non-direct `$JS.API.STREAM.MSG.GET.KV_<bucket>` with a wildcard `last_by_subj`, as `Sessions.read` does), and the pass is done only when the watcher has sent its end-of-first-pass nil and delivered a revision at or above that mark. Markers stay in the pass (no IgnoreDeletes): the newest entry can be one, and a marker removes the key. While waiting, the mark is re-read every 250 ms and only ever lowered, for an entry at the mark that vanished (a purge marker whose TTL ran out); it is never raised, so steady writes cannot hold a pass back.
- `Watch(ctx, tenant, fn func(topic string, msg *LogMessage, deleted bool)) (*RetainedWatch, error)` (ruling R33a; it returned `stop func()` before): `(*RetainedWatch).Stop()` is the old stop. `(*RetainedWatch).Sync(ctx) error` returns once the watch has been through every write to the tenant's keys acknowledged before the call: it reads the leader mark over the two key filters (`leaderMark`, as the first pass does) and waits until the watch's `seen` reaches it. `seen` is the highest revision of any entry the watch read and passed to `consume`, recorded after fn returned and whatever fn was told (a removal of a topic fn never held counts too, so Sync cannot stall on one); a restarted watch's first pass counts only once it ends, after its removals. While waiting the mark is re-read every 250 ms on a ticker and only lowered (an entry at the mark that left the stream before the watch read it). Default deadline 10 s; timeout or unreadable leader wraps `ErrUnavailable`; a watch that has ended fails at once with `ErrUnavailable`. Cost: one or two leader requests per call. Watch, as before: starts with the tenant's current messages, caught up to the leader mark (fn gets each as a put), and returns once it has, so a cache filled only by Watch is loaded when Watch returns; the broker's "SUBSCRIBE waits for the tenant's load" can wait on that. Then every change: a put (msg the new message), or a removal by Delete, an empty Put or expiry (an expiry arrives as a purge with reason MaxAge; both are handled) with `deleted` true and msg carrying only Tenant, Topic and Seq. Seq is the revision, 0 for a removal found by a resync. A removal fires only for a topic fn holds, a put only when its revision is above the last one fn saw, so each change fires once and in order. Never another tenant's key. fn runs on the watch's one goroutine, before Watch returns too (do not hold a lock fn takes), and must be short. ctx is the lifetime: the watch runs until ctx ends or stop. The start (watcher, mark, first pass) has its own bound, 10 s or ctx's deadline if sooner (nats.go's 5 s request timeout can end it first), and fails with ErrUnavailable. A watch whose subscription closes under it logs at Error and restarts with backoff (200 ms doubling to 5 s); the new first pass, caught up to a fresh mark, reports the puts fn missed and, as removed, held topics the pass did not read (marker gone). stop is idempotent and prompt while NATS is unreachable: it sets a flag, then waits for a running fn, and fn never runs after it. Do not call stop from fn.
- Watchers are stopped in the background and drained: nats.go's KV watcher blocks its subscription goroutine on a full Updates channel and only then closes it, and its Stop deletes the consumer with a request that waits while NATS is down.
- nats.go ends a KV watcher's subscription when the context it was created with ends, and uses that context, deadline or not, for the consumer create request. So each Watch watcher gets its own context under the watch's ctx, cancelled when that watcher is done, and the start bound is attached with `context.AfterFunc` only for the create call. Do not create a long-lived watcher with a short request context.
- `Put` checks QoS before the empty-payload branch, so an empty payload with QoS 3 is ErrInvalidInput, not a Delete.
- Test hooks: `Retained.onWatch` gets every KV watcher a Watch opens, `Retained.beforeRestart` runs in the gap before a restart, `Retained.afterOpen` runs after a watcher exists and before the mark is read (a write there is missing from the first pass but under the mark: a lagging replica, made deterministic).

retained_test.go (package cluster, `startCellConns` gives n connections on a three-server cell, `startRetained` one Retained each) covers the round trip with Props (ordered duplicate user properties, a payload format of 0, correlation data, CR/LF/NUL payload), replacement and an empty put, Delete seen by Watch with its revision, a 2 s expiry seen by Watch about 2 s later and gone from Load, tenant isolation (same topic in two tenants, a tenant whose token prefixes another's, `$SYS` in another tenant), `$SYS` under `==tenant` and absent from a `#` key listing, a watch restarted after its subscription was stopped (delete, update and new key in the gap, no event for the unchanged key), the resync of unseen keys, stop and ctx end, invalid input, `TestRetainedFirstPassReachesLeaderMark` (a put and a delete marker made in `afterOpen`: Load and Watch's first pass must include them; it fails when the mark is ignored), `TestRetainedWatchSync` (a put on another node is through a 300 ms slow fn when Sync returns, over five rounds; three deletes of never-held topics do not stall Sync; a held topic's delete is reported when it returns; Sync on a stopped watch is ErrUnavailable; it fails when seen advances before fn or counts only puts), 40 rounds of put on one node and Load on another, and the start bound with the only server down.

## Control bus

`NewControl(c *Conn, cfg Config) *Control` over stream `Config.ControlStream()` (`TETHER_CTL_<CELL>`, subjects `ctl.>`, MaxAge 1 h; Provision first). An event is JSON on `ctl.<kind>`. Each node reads with one ordered consumer (filter `ctl.>`) that starts at the stream's last sequence + 1 when Start runs (an explicit sequence, not "new", for the same reason as the log Reader). Every node, the publisher included, applies each event published while its Control runs exactly once and in stream order: the ordered consumer recreates itself after a gap from the last sequence it delivered, and a sequence at or below the last one handled is dropped. Events published while a node was down are not replayed to it. The connection's NoEcho does not matter: deliveries come from the server.

- Kinds (constants) and their exported payload structs, snake_case JSON: `KindKeyInvalidated` "key.invalidated" `KeyInvalidated{KeyID, Disconnect, RotatedAt, GraceEnds}` (`key_id`, `disconnect`, `rotated_at`, `grace_ends`; times `omitzero`; RotatedAt is there for the reactor's KeyRotated, which needs it for ExpirePrincipal), `KindRoleChanged` "role.changed" `RoleChanged{RoleID}`, `KindSubjectChanged` "subject.changed" `SubjectChanged{Kind, ID}`, `KindTenantUpdated` "tenant.updated" `TenantUpdated{TenantID}`, `KindSessionKick` "session.kick" `SessionKick{Tenant, ClientID}`, `KindSessionDelete` "session.delete" `SessionDelete{Tenant, ClientID}`.
- A kind is dot-separated tokens of `[-_A-Za-z0-9]`, at most 128 bytes, so `ctl.<kind>` is a literal subject. Anything else wraps `tether.ErrInvalidInput`.
- `Subscribe(kind, fn func([]byte)) error`: registers a handler; several per kind run in registration order. No NATS call; before or after Start, but an event that arrives before its kind has a handler is dropped, so register before Start. Kinds nobody subscribed to are ignored (Debug log); matching is exact (`session.kick.extra` is not `session.kick`). fn gets the event's JSON, shared by the kind's handlers (do not modify). Handlers run on the bus's one goroutine, one at a time: they must not block (hand work to your own goroutine) and must not call Stop. nil fn: ErrInvalidInput; after Stop: wraps ErrUnavailable.
- `Publish(ctx, kind, v any) error`: `json.Marshal(v)`, publish, wait for the JetStream ack. Needs no Start. 10 s without a deadline; timeouts wrap ErrUnavailable (the event may still have been stored).
- `Start(ctx) error`: creates the consumer (it exists on the server when Start returns) and starts the read goroutine. ctx bounds the start only (10 s default). A second Start is an error unless the first failed; after Stop it wraps ErrUnavailable.
- Replacement (CHAOS-2 audit): the consumer is built like a log Reader's, with `MaxResetAttempts` 1 and a stall watch (the control stream's last sequence against the last event handled, one stream info per `stallAfter` while idle). When it fails or stalls, `serve` logs at Error and `reopen` makes a new consumer from the last event handled + 1, retrying with backoff (200 ms doubling to 5 s) until it works or Stop, so no event is skipped or run twice. `last` moves under the handler mutex after the stop check, so a halted run's last is final.
- `Stop()`: idempotent, also before Start. It sets a stop flag, then waits for a running handler, and no handler runs after it returns; the iterator stop and the consumer delete run in the background, so it is prompt while NATS is unreachable (a recreate attempt can take 10 s). It also ends a replacement in progress. `Control.heartbeat` is the pull heartbeat; `resetAttempts` and `stallAfter` as on Log (tests set them).
- Locking: `Control.mu` guards the handler map and the lifecycle flags and is never held across a NATS call; a handler snapshot is copied under it per event.

## Shared

Shared subscriptions across the cell (spec "Shared subscriptions", rulings R5, R34, R35). `NewShared(c *Conn, cfg Config, l *Log) *Shared` (the log stream must exist: Provision first; cfg names the node). A group is `(tenant, group, filter)`, the shared subscription `$share/<group>/<filter>` of one tenant, and has two halves:

- QoS 1/2: one durable pull consumer per group on the log stream, shared by the cell. Name `tether_sh_` + the first 20 bytes of sha256(tenant NUL group NUL filter) in hex (also the queue group name), so any group and filter give a valid, distinct, tenant-scoped name. One filter subject, `subject.LogFilter(tenant, filter)`: the filter's levels encoded as the log encodes them, `+` as `*`; for a trailing `#` the levels before its parent level and then `>` (`a/b/#` reads `d.<tenant>.a.>`; `a/#`, `+/#` and `#` read `d.<tenant>.>`), because one subject cannot cover a parent and its children. Messages are matched with `topic.Match` after they arrive (that also keeps a wildcard-first filter off `$` topics, which the log keeps under the plain tenant token) and the tenant is checked; the rest is acked at once (`skipped`). Config: DeliverNew, explicit ack, `AckWait` 30 s (`defaultSharedAckWait`), `MaxAckPending` 1024 (`sharedMaxAckPending`, the group's unacked messages across the cell), MaxDeliver unlimited, `InactiveThreshold` = the log stream's MaxAge (0, never, when the log keeps everything), so a group with no member anywhere keeps its place like the log keeps messages. `CreateOrUpdateConsumer` with the same config from whichever node needs it.
- QoS 0: a NATS queue group (same name) on `subject.QoS0Filters(tenant, filter)`, on the queue connection. The Router's `Tether-Id` deduplicates per group within 2 s, as in the Router (the trailing `#` pair of subjects is disjoint, so it is a guard). NATS picks one subscriber per message cell-wide and prefers the publishing server's own, so with members on the publishing node they get its QoS 0.

- `Join(tenant, group, filter string, deliver SharedDeliver) (leave func(), err error)`: adds a member on this node and returns its leave (idempotent). The first member on the node subscribes the queue group (and flushes, so the node's own server has the interest when Join returns), creates or opens the consumer and starts the pull loop; the last leave unsubscribes and stops the loop; the consumer stays on the server. Validation: non-empty tenant, a group of one level without `/`, `+`, `#` or NUL, `subject.CheckTopic` on filter and group, `topic.Valid(filter, true, 1024)`, no nested `$share`, non-nil deliver; all wrap `tether.ErrInvalidInput`. NATS failures wrap ErrUnavailable when NATS is unreachable; after Close Join wraps ErrUnavailable. Join bounds its NATS work by 5 s.
- `SharedDeliver func(msg LogMessage, done func(error)) error`: hands one message to one member. Return nil once the member took it and call done exactly once later: nil when the member is through with it (QoS 1 PUBACK, QoS 2 PUBCOMP, a QoS 0 delivery written), an error when the member was lost before that. A non-nil return means not taken, and done must not be called. done may run before deliver returns and from any goroutine; only its first call counts. QoS 0 messages (QoS 0, no Seq, no Origin or ClientID, Retain from the `Tether-Retain` header, Props from headers) ignore done.
- `ErrMemberBusy`: what deliver returns (wrapped) when the member cannot take it now but may later. Members on the node are tried in turn, starting from a round-robin index (fair per node). A QoS 1/2 message none took: naked with a 250 ms delay (`sharedBusyDelay`) when there were no members (a leave raced) or any was busy; acked and dropped when all refused with another error (their grants), as mochi drops a shared delivery the chosen client may not read. A QoS 0 message none took is dropped (`dropped`).
- Pull loop (`sharedPull`): one `Fetch` at a time, 16 messages (`sharedPullBatch`, so one node does not hoard a burst), waiting at most `fetchWait` (2 s), each fetch read to its end. A continuous pull iterator leaves its pull request on the server when it stops, and a message the server sends to the abandoned inbox waits the whole ack wait; a fetch read to its end hands every message to `handle`, which naks it (250 ms delay) once the loop is stopped. stop is prompt (a flag and a channel), also while NATS is unreachable; the goroutine ends after the fetch in progress. A consumer deleted or not found (inactive threshold) is made again (`consumerGone`: a fetch on a consumer that is gone fails with nats.go's `ErrNoResponders`, the server's 503, unless it was deleted under a running fetch, which says `ErrConsumerDeleted`); every failure retries with backoff (200 ms doubling to 5 s). deliver runs on the loop's goroutine for QoS 1/2, one message at a time in the order the node got them, and on NATS dispatch goroutines for QoS 0: keep it short.
- Pending messages (handed and not done) are kept alive by one ticker per Shared that sends `InProgress` every AckWait/3, so a slow member keeps its message and only a lost node (no ticker, no nak) lets JetStream redeliver after AckWait. A member that leaves keeps its pending messages alive until done is called: the caller must call done for every message it took (the broker does at session end). done(nil) for a QoS 2 message (the member has it pinned) acks with `DoubleAck` and keeps the message pending, kept alive, until JetStream confirms the ack (`ackPinned`, one goroutine per QoS 2 message, resent every 100 ms doubling to 2 s, at most 10 min, stopped by Close): a fire-and-forget ack lost on the way let JetStream give the message to another member after AckWait, two deliveries of one QoS 2 [MQTT-4.8.2-5]. QoS 1 keeps the fire-and-forget `Ack` (a duplicate is allowed).
- `Close()`: stops every group of the node, stops the ticker, naks what is still pending (best effort), makes Join fail; idempotent; does not close the Conn or delete consumers.
- Locking: `Shared.mu` guards the group map and pins; each group's `mu` serialises its first Join and last leave and is held across their NATS calls (never while `Shared.mu` is wanted; order group mu, then Shared.mu, as in the Router); `mmu` guards the member list; `pmu` the pending set. deliver is never called under any of them.
- Test fields (unexported): `ackWait`, `fetchWait`, `heartbeat` (fetch heartbeat, used only when under half the fetch wait), `wrapMsg` (wraps every fetched message); counters `delivered`, `acked`, `naked`, `skipped`, `dropped`, `recreated`, `ackRetries` (QoS 2 acks sent again).
